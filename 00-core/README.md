# 00-core · 共享基础设施

> 本文件夹**不对应某一个 Agent 模块**。它装的是被多个模块复用的地基。
> 代码位置：`00-core/src/copilot/`

## 为什么共享代码要单独成文件夹

源码的依赖关系是**分层**的，不是平铺的。实测出来的依赖图：

```
textseg（叶子，无依赖）
   └── evidence  ──────────────┐   E2 的核心能力
          ├── retrieval  ◀─────┤   E3 查重将来也要用
          ├── memory     ◀─────┤   跨阶段复用
          └── graph      ◀─────┘   编排层（还依赖 memory / retrieval）
```

关键事实：**`evidence` 虽然由 E2 负责，但它是基础能力** ——
检索、记忆、编排都依赖它。如果把 `evidence` 塞进 `00-core/docs/`，
就会出现 "`00-core` 依赖 `e2-citation`" 这种倒挂。

因此把这些"被多方复用的地基"统一放在 `00-core/`，
含义是 **"共享基础设施"**，而不是"某个 Agent 的代码"。

E2 模块自己的 README 会说明它**如何复用**这里的 `evidence`。

### 明确不做的部分（应用层）

早期曾留有 `api/` `guard/` `mcp/` `obs/` `routing/` `skills/` 六个**空占位包**，
现已**删除**。

理由：本项目目标是「学习技术栈 + 跑通最小验证系统」，不扩展到应用层。
而这六个空文件夹会让人误以为"这些能力已经规划好了" —— **那是噪音**。
将来真要做，应当先写清设计再建目录，而不是先留空壳。

| 不做 | 属于 |
|---|---|
| HTTP API / 服务化 | 应用层 |
| MCP / 工具接入 | 应用层 |
| 可视化可观测性（trace 面板 / 重放 UI） | 应用层 |
| 模型难度路由（无真实模型可路由） | 应用层 |
| Skills 固化 | 应用层 |

**注意：能力本身不删，只是不做外壳。**
"审计"能力在 `memory/` 的 `forget_log` 里已实现，只是不提供审计导出接口；
"可观测"的基础在 checkpointer 里已有，只是不做可视化。

### 为什么 `textnorm` 与 `overlap` 放在这里（而不是某个 Agent 模块里）

因为它们**被多个模块同时使用**，而且**必须只有一份实现**：

| 工具 | 如果各模块各写一份会怎样 |
|---|---|
| `normalize` | 两侧口径不一致 → 比对结果"看起来差一点"，**且不报错** —— 本项目已经踩过这个坑（见 e3 相关记录） |
| `longest_common_substring` | "文本有多像"会有两个判定标准，两处结论可能矛盾 |

这正是 `00-core` 存在的意义：**放"被多方复用的地基"**。

# 检索评测指标怎么读

> 实现在 `retrieval/metrics.py`。本节的数字全部来自
> `reports/retrieval_ablation.md`（60 篇论文 / 120 条查询 / 6 个变体）。

## 一、所有指标都建立在"三方"上

不管哪个指标，输入永远是这三样：

```
① query        一条查询（这里就是论文标题）
② ranked       检索器返回的**有序**文档列表
③ gold         标准答案集合（哪些文档算"对"）
```

**指标就是这三样东西的算术。** 理解了这一点，四个指标都能自己推出来。

## 二、逐指标拆解

### 手算例子（贯穿下面四个指标）

```
gold   = {P1, P3}                        ← 标准答案有 2 篇
ranked = P7, P1, P9, P3, P2              ← 检索返回的前 5

位置:    1    2    3    4    5
命中了:  ✗    ✓    ✗    ✓    ✗
```

### ① Recall@k —— "该找的，找到了几成"

```python
Recall@k = |ranked[:k] ∩ gold| / |gold|
```

| k | 计算 | 结果 |
|---|---|---|
| 1 | 命中 0 条 / 共 2 条 | **0.000** |
| 3 | 命中 1 条（P1）/ 共 2 条 | **0.500** |
| 5 | 命中 2 条（P1, P3）/ 共 2 条 | **1.000** |

**回答的问题**：漏了多少。

**会被什么骗**：它**完全不看位置**。P1 排第 1 和排第 100 都是"命中"。
如果用户只想看最相关的一两篇，Recall@k 会给你虚假的安心。

**★ 使用前提**：`k` 必须 ≥ `|gold|`，否则**上限到不了 1**。
本项目的 gold 恒为 1 篇，所以 Recall@k 实际退化为"命中 / 未命中"。

### ② Precision@k —— "前 k 个里，有多少是对的"

```python
Precision@k = |ranked[:k] ∩ gold| / k
```

| k | 计算 | 结果 |
|---|---|---|
| 1 | 0 / 1 | **0.000** |
| 3 | 1 / 3 | **0.333** |
| 5 | 2 / 5 | **0.400** |

**回答的问题**：白看了多少。

**会被什么骗**：**它的天花板是 `|gold| / k`**。
gold 只有 1 篇时，Precision@5 最高只能是 0.2 —— 数字看起来很差，
但那不是检索器不行，是**这个指标在这种设定下没意义**。

**★ 所以本项目的消融报告里没有列 Precision**：
`gold` 恒为 1 时，`Precision@k = Recall@k / k`，
只是把 Recall 除以 k，**不携带任何新信息**。

### ③ MRR —— "第一个对的排在第几"

```python
MRR@k = mean( 1 / 第一个命中的位置 )      # 没命中记 0
```

上例：第一个命中在**位置 2** → 这条查询得分 `1/2 = 0.500`。

**回答的问题**：用户要翻几条才看到想要的东西。

**为什么用倒数**：位置 1 → 1.0，位置 2 → 0.5，位置 3 → 0.333。
**位置越靠后惩罚越"软"**，而不是断崖式归零。

**会被什么骗**：**只奖励第一个命中**。
第 2、第 3 篇也对，但完全不计 —— 所以它适合"只要那一篇"的场景，
不适合"要把相关文献都找全"的场景。

### ④ nDCG@k —— "整体排序质量"，位置加权

```python
DCG  = Σ  1 / log2(位置 + 1)      # 只累加命中的
IDCG = Σ  1 / log2(位置 + 1)      # 理想排序：所有对的都排最前
nDCG = DCG / IDCG
```

上例：

```
DCG  = 1/log2(3) + 1/log2(5) = 0.631 + 0.431 = 1.062     ← 位置 2 和 4
IDCG = 1/log2(2) + 1/log2(3) = 1.000 + 0.631 = 1.631     ← 理想是位置 1 和 2
nDCG = 1.062 / 1.631 = 0.651
```

**回答的问题**：把结果整体排序的质量如何（不只看第一个）。

**为什么除以 IDCG**：不同查询的 gold 数量不同，直接比 DCG 不公平。
归一化后不同查询之间可以平均。

**会被什么骗**：本项目的 gold 没有分级相关性标注，只能用**二值**（对/不对）。
二值时 nDCG 与 MRR 高度相关，只是**折损更温和**。

### 四个指标的关系（一张表记牢）

| 指标 | 回答 | 看位置吗 | 看全部命中吗 | 主要误用 |
|---|---|---|---|---|
| **Recall@k** | 漏了多少 | ❌ | ✅ | k < \|gold\| 时上限 < 1 |
| **Precision@k** | 白看了多少 | ❌ | ✅ | 天花板 = \|gold\|/k，gold 少时不可比 |
| **MRR** | 第一个对的排第几 | ✅ | ❌ | 忽略第 2 个之后的命中 |
| **nDCG@k** | 整体排序好不好 | ✅ | ✅ | 二值下与 MRR 高度相关 |

## 三、★ 用指标反推分布（一个实用的一致性检查）

本项目的变体 D：`Recall@1=0.842`、`Recall@5=0.967`、`Recall@10=0.983`、
`MRR=0.895`，共 120 条查询、gold 恒为 1。

**反推排名分布**：

| 区间 | 查询数 | 怎么算 |
|---|---:|---|
| 排第 1 | 101 | 0.842 × 120 |
| 排 2–5 | 15 | 116 − 101 |
| 排 6–10 | 2 | 118 − 116 |
| 完全没进前 10 | 2 | 120 − 118 |

**验证 MRR 是否自洽**：

```
最好情况（15 条都排第 2，2 条都排第 6）:
  (101×1 + 15×0.5 + 2×1/6) / 120 = 0.907
最坏情况（15 条都排第 5，2 条都排第 10）:
  (101×1 + 15×0.2 + 2×0.1) / 120 = 0.868
实测 MRR = 0.895 ∈ [0.868, 0.907]  ✓ 自洽
```

**这个检查的用处**：如果 MRR 落在区间外，说明某个指标算错了，
或者汇总时有 bug。**比逐个盯着数字看可靠得多。**

> 顺带一个观察：本项目 6 个变体**全部满足 `nDCG > MRR`**
> （0.897>0.876、0.892>0.869、0.882>0.854、0.917>0.895、0.810>0.763、0.868>0.829）。
> 这不是巧合 —— nDCG 在深位置折损更温和（位置 2：`1/2=0.5` vs `1/log2(3)=0.631`），
> 所以系统性偏高。**两个指标不能混着比较。**

## 四、Bootstrap 置信区间

### 为什么需要

单次跑出的 `Recall@5 = 0.967` **说明不了任何稳定性问题** ——
换一批查询，它可能是 0.93 也可能是 0.98。没有区间就无法判断
"改了策略后 +1.5% 到底是真提升还是噪声"。

### 怎么算（`bootstrap_ci`）

```
① 从 120 条查询的得分里，有放回地抽 120 个        ← 2000 次
② 每次算一个均值 → 得到 2000 个均值
③ 取 2.5% 和 97.5% 分位数 → 95% 置信区间
```

**为什么固定种子**（`seed=20260101`）：不固定的话，同一份数据每次跑出
不同区间，**项目引以为傲的可复现性就没了**。报告里的区间必须能重跑出来。

### 怎么读

> `Recall@1 = 0.842 [0.78, 0.90]`
> 意思是：如果换一批来自同一总体的查询，均值大概率落在 0.78–0.90 之间。

**区间宽度告诉你"这个数字有多不确定"**：
`[0.78, 0.90]` 宽 0.12 —— 说明 120 条查询的样本量**只能分辨较大的差异**。
想检出 2% 的提升，需要多得多的查询。

### ★★★ 最重要的一条：CI 重叠 ≠ 没有显著差异

本项目的报告里有一句容易被误读的话：

> 本次 15 项指标对比中，**没有任何一项的置信区间不重叠**。

如果只看这句，会得出"所有变体都没差别"的结论 —— **这是错的**。
因为有三项在配对检验下**显著**：

| 比较 | 指标 | 变体 C | 变体 D | 配对检验 |
|---|---|---|---|---|
| C → D | MRR | 0.854 **[0.80, 0.91]** | 0.895 **[0.85, 0.94]** | **显著**，p(BH)=0.0074 |

两个区间在 `[0.85, 0.91]` **明显重叠**，但差异显著。为什么？

```
两个 CI 各自是**边际**的：把 120 条查询当成两批独立样本
  → 包含了"查询难度"这个巨大的共同方差

配对检验看的是**逐查询差值** d_i = D_i − C_i
  → 查询难度在相减时**抵消了**
  → 差值的方差远小于各自均值的方差
  → 同样样本量下功效高得多
```

**一句话**：两个 CI 重叠，只能说明"两批独立样本可能来自同一分布"；
而这里它们**不是独立样本** —— 它们跑的是**同一批 120 条查询**。

> 这正是本项目方法论上的关键教训：
> 第一版消融用独立 CI 比较，结论只能是"CI 重叠，无法断言"；
> 改成配对检验后才检出真实差异。详见根 README §13.3。

## 五、本项目评测设定的限制

| 限制 | 影响 |
|---|---|
| **gold 恒为 1 篇**（known-item search） | Recall 退化为命中率；Precision 无信息量；MRR 与 Recall@1 高度相关 |
| 查询由标题生成（`title` / `title_head`） | 比真实用户提问简单，绝对值偏高 |
| 只有 120 条查询 | 只能检出较大效应；CI 较宽 |
| 二值相关性 | 无法用分级 nDCG；不能区分"很相关"与"稍微相关" |
| 语料刻意窄（60 篇 cs.IR × LLM） | 天然难负例，但结论不能外推到通用检索 |

# 模型接入层 `llm.py`

## 为什么不用 `openai` SDK

本系统只用一个接口（`POST /chat/completions`）。
一个 SDK 换来的是：额外依赖、版本兼容问题、**隐式的重试行为**（你无法确定它到底调了几次）。

而 `httpx` 已经因为 LangGraph 装上了 —— **用现成的，不新增依赖**。

## 配置全部来自环境变量

| 环境变量 | 作用 | 回退 |
|---|---|---|
| `COPILOT_LLM_API_KEY` | 密钥（必填） | `OPENAI_API_KEY` |
| `COPILOT_LLM_BASE_URL` | 接口根地址（`…/v1`） | `OPENAI_BASE_URL` |
| `COPILOT_LLM_MODEL` | 模型名 | `OPENAI_MODEL` |

写在 `05-format/.env` 里即可（`.gitignore` 已覆盖 `.env` 与 `.env.*`，但保留 `.env.example`）。

**是否真的要 `.env`**：本项目**不强制**。没配密钥时 E4/E5 自动退回 `StubRewriter`，
如实报「需人工改写」—— 整条链路仍可跑通。

## ★ 两条与密钥有关的设计

**① `repr` 脱敏**

```python
LlmConfig(base_url='https://…/v1', model='gpt-6.1-sol', api_key=<已设置 51 字符>, …)
```

**只显示"有没有配"和长度，不显示密钥的任何片段。**

理由很实际：**调试时最常做的事就是打印配置**。
如果 `repr` 里带密钥，一次 `print(cfg)` 就可能把密钥写进日志或截图。

**② 异常消息里不带密钥**

`LlmError` 的消息会被写进报告（报告是要给人看、可能被分享的）。
所以错误路径上只保留 HTTP 状态码与服务端返回的错误描述，绝不回显请求头。

有专门的测试锁住这两条。

## 三个函数

| 函数 | 作用 |
|---|---|
| `load_env(path=None)` | 从 `.env` 加载（**显式调用**，不做 import 副作用） |
| `LlmConfig.from_env(...)` | 装配配置；缺项时报错**说清缺哪个变量** |
| `chat(messages, config=…, n=1)` | 调 `/chat/completions`，返回候选文本列表 |
| `ping(config)` | 探活，返回可用模型 id 列表（**GET `/models`**） |

## 踩过的坑

**`ping` 误用 POST**：`/models` 是 GET 接口，早期实现复用了 POST 传输层，
结果一路 404，排查了半天才发现是方法错了。
现在 `ping` 用独立的 `GetTransport`，并有测试锁住。

**`n` 参数可能被服务端静默忽略**：实测某个 OpenAI 兼容端点请求 `n=3` 只返回 1 个候选，
而且**不报错**。静默失效比报错更糟 —— 调用方以为"我拿 3 个挑最好的"，其实一直只拿 1 个。
现在 `LlmRewriter` 用 `n_ignored` 计数把这个事实暴露出来。

## 已知局限

| 局限 | 说明 |
|---|---|
| 只支持 `/chat/completions` | 不支持 function calling / 流式 / 多模态 |
| 无 token 计费统计 | 成本不可见；只统计调用次数 |
| 无并发控制 | 批量改写是串行的，慢（单次 10–30 秒） |
| 重试策略简单 | 只对超时/429/5xx 线性退避，没有抖动 |

# 配对二分类：通过率该怎么比

接入真实模型后出现了新的评测问题：**通过率**（达标 / 未达标）不是一个连续值，
不能直接套用 Wilcoxon 或 t 检验。

新增的两个工具（`stats.py`）：

| 函数 | 作用 |
|---|---|
| `mcnemar_test(a, b)` | 配对二分类检验，返回 `(b_count, c_count, p)` |
| `paired_proportion_diff_ci(a, b)` | 配对 bootstrap，返回 `(diff, lo, hi)` |
| `compare_proportions(...)` | 上面两个一起算，返回字典便于写报告 |

## 为什么必须换检验

通过率是 0/1 数据，一次调用只贡献 0 或 1。

**真正携带信息的是"不一致对"**：

```
A 通过 & B 不通过   (b)
A 不通过 & B 通过   (c)
两边都通过 / 都不通过 → 对"哪个配置更好"没有发言权
```

把 0/1 直接喂给连续型检验，会把这少数翻转的信息**摊薄到全部样本上**，
功效低得多。这是「检验要和数据类型匹配」的一个具体例子。

**为什么用精确二项而不是卡方近似**：`b + c` 常常小于 25，
此时卡方近似不可靠（scipy 文档也这么建议）。

## 与连续指标的对应关系

| 场景 | 用什么 | 这里 |
|---|---|---|
| 连续指标（Recall / MRR / 得分） | Wilcoxon + 差值 CI + Cohen's dz | `compare_paired` |
| **二分类（通过率 / 命中率）** | **McNemar + 差值 CI** | **`compare_proportions`** |

两者**都要求配对**（同一批样本），理由相同：
同一批样本的难度相关，配对能消掉这部分方差。

## 已用它做的实验

`eval/run_rewrite_eval.py` —— E4 改写通过率评测，对照三组配置
（v1/v2 提示词 × 单次/重试）。详见 `reports/rewrite_pass_rate.md`。

# 附：主 Agent（`copilot/orchestrator/`）

> 代码：`00-core/src/copilot/orchestrator/` · 测试：`00-core/tests/test_orchestrator.py`（44 项）
> 演示：`python 00-core/examples/demo_orchestrator.py`
> 入口：`from copilot.orchestrator import run_request`

## 为什么它属于共享层，而不是某一个阶段

主 Agent 要调**全部六个阶段**，所以它不能住在任何一个阶段里 ——
否则那个阶段就成了"上层"，其他阶段反过来依赖它。

它属于 L1 编排层：**只依赖 `contracts`（知道有哪些阶段和节点）**，
对具体阶段的依赖是**运行时的延迟 import**（`execute.py` 里的 `_run_a` 等适配器）。

## 三层路由

| 层 | 决定 | 实现 | 数据 |
|---|---|---|---|
| ① | 调哪几个**阶段** | `plan.STAGE_CUES` | `PlanStep.stage` |
| ② | 阶段里跑哪几个**节点** | `plan.NODE_CUES` + `NODE_DEPS` | `PlanStep.nodes` |
| ③ | 每个节点用什么**模型** | `router.ModelRouter` | `PlanStep.model` |

三层的结果全部落在 `PlanStep` 上 —— **一个 step 就是一次"用某个模型跑某阶段某几个节点"**。

## 四个文件各自的职责

| 文件 | 职责 | 不做什么 |
|---|---|---|
| `models.py` | 数据结构：`Plan` / `PlanStep` / `StepResult` / `OrchestrationReport` | 不含任何调度逻辑 |
| `plan.py` | 把请求变成 `Plan`（规则版 + 模型版） | 不执行、不知道阶段内部长什么样 |
| `router.py` | 决定每个 step 的模型 | 不自己造模型，只是一张登记表 |
| `execute.py` | 按 `Plan` 调阶段、按 `only` 收窄节点 | **不重排顺序**、不重试到成功 |

## 两条必须记住的规则

**① 收窄只减不增。** 关键词只能让一个阶段跑得更少。多跑用户没要求的节点是错。

**② 依赖必须补齐。** `NODE_DEPS` 记录"谁读谁的 state"：

```python
NODE_DEPS = {
    "A2": ("A1",), "A3": ("A1",),   # 读 A1 的 signals
    "B2": ("B1",),                  # 综述要用 B1 检索出的文献
    "D2": ("D1",),                  # 分章写作读 D1 的大纲
    "F2": ("F1",),                  # 改写要用 F1 定位出的片段
}
```

不补齐的后果不是"报错"，而是**下游静默出空报告** —— 那更危险。

## 缺输入时的行为

```python
run_request("帮我降重", context={"draft": text})
# F ⏭ 跳过：缺少输入：外部查重 / AI 检测报告
# 整体结论：⚠️ 没有任何阶段被执行
```

**跳过 ≠ 通过。** `OrchestrationReport.can_submit` 只在
"有阶段真的跑过、且都通过"时为真。

## 为什么规划先用规则

| 理由 | 说明 |
|---|---|
| 可测 | 给一句话，断言 `Plan` 里有哪几个 step —— 模型版做不到确定性断言 |
| 免费 | 问"帮我看看格式"先烧 3000 token 做规划很浪费 |
| 可回退 | 模型不可用时系统仍然能用 |
| 可对照 | 规则版是模型版的 baseline |

`LlmPlanner` 已有接口（传一个 `(prompt) -> JSON 字符串` 的 callable），
失败时**直接降级到规则版**并记一条 note —— 不做重试。

## 实测

```
帮我看看格式                    → E[全部]
字体和字号对不对                → E[E1]
帮我降重                       → F[全部]
这段改写一下                   → F[F1/F2]     ← 依赖被补齐
引用来源靠谱吗                 → D[D4]
帮我做个选题                   → A[全部]      ← 阶段名不收窄
看一下研究空白和趋势            → A[A1]
把格式整理一下，再看看有没有重复的段落 → E[全部] + F[F1/F2]
随便说点什么                   → （没有匹配到阶段）
```

## 附二：LangGraph 版主 Agent（`orchestrator/graph.py`）

> 演示：`python 00-core/examples/demo_orchestrator_graph.py`
> 入口：`from copilot.orchestrator import run_request_graph`

### 图长什么样

```
START → plan ─┬─(有 step 且需确认)→ approve ─┬─(同意)→ pick
              │                              └─(拒绝)→ summarize
              ├─(有 step 不需确认)→ pick
              └─(没匹配到阶段)→ summarize

pick ─┬─(还有 step)→ run → pick        ← 循环
      └─(跑完了)→ summarize → END
```

`pick → run → pick` 就是手写 `for` 循环在图里的等价形式 ——
**LangGraph 里做动态工作流的写法是「用条件边表达 while」**。

### 为什么只有一个 `run` 节点

走哪个阶段由 `plan` 节点决定，**不需要用边来表达**。
`run` 节点按 `step.stage` 分派到对应 `run_*`；
节点级路由（只跑 E1）通过 `only` 参数发生在**节点内部**。

做成 6 个阶段节点不会多出任何能力，只会让图更花。

### 两个它才有的能力

**① `interrupt` 计划确认**

```python
run = run_request_graph("帮我降重", context=..., require_approval=True,
                        checkpointer=InMemorySaver(), thread_id="t1")
if run.needs_approval:
    print(run.pending)       # 跑哪几个阶段、哪几个节点、用什么模型
    run = run.resume(True)   # 点头才执行
```

`plan_only` 做不到这件事：要"先看计划"只能调两次，中间状态没地方存。

**② checkpoint 断点续**

状态存在 checkpointer 里，进程重启也能从断点继续。
为此给契约加了 `from_dict`：`StageReport.from_dict(x.to_dict())` 必须一致。

### 状态里能放什么

| 能放 | 不能放 |
|---|---|
| `plan`（dict）、`cursor`、`results`（dict 列表）、`approved` | `context` 里的 `rewriter` / `formatter` / `generator` |

`context` 通过**闭包**进节点（图是每次请求现建的）。
把它塞进状态会让 checkpoint 序列化失败。

### 两版必须等价

`test_orchestrator_graph.py` 里有一组参数化测试：同一请求下，
`run_request`（走图）与 `run_request_graph`（直接用图对象）的
**计划、节点范围、结论**必须完全一致 —— 它们是同一条实现路径。

理由很直接：**换编排方式不能改变业务行为** —— 否则用户不知道该信哪个。

### 包级导入是延迟的

`orchestrator/__init__.py` 用 `__getattr__` 延迟导入 `graph`，
所以 `import copilot.orchestrator` 本身不会拉起 langgraph；
只有真正调用 `run_request` 时才会。有测试守着这一条。
