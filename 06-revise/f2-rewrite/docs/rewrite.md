## 本模块解决的核心问题

> **外部查重报告指出了哪些段落重复，把它们改写成自己的表述 —— 并且能证明改完之后还是对的。**

**本模块不做查重。** 输入是 E3 解析定位好的问题清单。

# 第一部分：设计

## 输入 / 输出契约

| | 内容 |
|---|---|
| **输入** | E3 的问题清单（已定位的重复片段 + 报告给的来源文献/原文，若有） |
| **输出** | 每条片段的：改写建议 / 受保护标记 / 降重效果（数字）/ 保真结论 |
| **不做** | 不做查重、不自动替换原文（只给建议） |

## ★ 一个必须先想清楚的歧义：拿什么当"重复的对方"

降重的目标是**降低与原出处文字的重叠**。但"原出处"未必拿得到：

| 情况 | 报告里有 | 怎么度量 |
|---|---|---|
| **A** | 报告给出了被匹配的**来源原文** | 直接度量「改写后 ↔ 来源原文」的重叠 —— **这是正确的做法** |
| **B** | 报告只给了**用户自己那段重复文字** | 只能度量「改写后 ↔ 用户原句」的重叠 —— **这是代理指标** |

**为什么要把这件事说清楚**：情况 B 下的度量**不等于**真实的降重效果。
改写后与自己的原句不重合，**大概率**也与来源不重合 —— 但这是推理，不是测量。

**因此本模块的做法是**：有来源原文就按 A 度量并标为"直接度量"；
只有用户原句就按 B 度量并**在报告里明确标注这是代理指标**。
**不把代理指标当成真实降重率报给用户。**

## 七个子部分：作用与「为什么需要」

### ① 改写单元切分 `units.py`

**作用**：把定位到的重复片段切成**可独立改写的句子**。

**为什么需要**：报告给的片段可能跨好几句。整段丢给模型改有三个问题：
- **保真风险大**：一次改一大段，很容易在某一处悄悄改变原意；
- **无法定位失败点**：改完发现某句不对，不知道是哪句的问题；
- **无法部分采用**：用户可能只想改其中一句。

切成句子后，逐句改、逐句验、逐句给效果 —— 可控得多。

### ② 受保护片段识别 `protected.py` ✅

**作用**：识别**不能改**的内容并从改写范围里排除。

**为什么需要**：**降重的第一原则是不能改的东西绝不能改。**

| 类型 | 为什么不能改 |
|---|---|
| **引号内的直接引用** | 改了就不再是"引用"，而是**篡改他人原文** |
| **带参考文献标注的句子** | 改了会切断引用关系 —— 从"重复率高"变成**学术不端** |
| **专业术语** | 改了反而不准确（见 ③ 的策略） |
| **数据 / 公式** | 改了就错了 |

判据复用 E2/E3 的引用识别逻辑（`citation_status`）——
**"哪句话属于规范引用"的判定标准只能有一份**，两份实现迟早不一致。

### ③ 改写策略选择 `strategy.py`

**作用**：按内容类型决定改写空间的大小。

**为什么需要**：**不同内容的改写空间完全不同**，用同一种策略会出错：

| 内容类型 | 改写空间 | 正确做法 |
|---|---|---|
| **方法描述** | 中（术语保留，改句式） | 重述表达方式 |
| **结论陈述** | 大（可换视角） | 重述 + 换表述角度 |
| **定义 / 定理** | **几乎没有** | ★ **建议规范引用，而不是改写** |
| **实验数据** | 无 | 不得改动 |

**★ 最重要的一条：有些内容本来就不该改写，而应该引用。**
如果系统硬要改写一个定义，产出的东西既不像原文、**也可能不准确** ——
那比"重复率高"糟糕得多。策略里必须有一条
**「建议引用而非改写」**，并且要能让用户理解为什么。

### ④ 改写生成 `rewriter.py`（模型接入点）

**作用**：调用模型产出改写候选。

**为什么需要**：这是**必须用模型**的一环 —— 规则做不到真正的重述。
（对比 E1/E2/E3 全部可以确定性实现，这一环不行。）

**关键设计：做成可插拔接口。**

```python
class Rewriter(Protocol):
    name: str
    def rewrite(self, text: str, *, strategy, context) -> list[str]: ...
```

好处有三：
1. **没有模型时全链路仍可跑通** —— 用 stub 实现（返回原句加个标记），
   测试与联调不阻塞；
2. **换模型不改其它代码**；
3. **可以做对照**：不同模型/提示词的降重效果可以量化比较（接 `stats.py`）。

### ⑤ 保真校验 `fidelity.py` ★

**作用**：确认改写后的句子**仍然表达同一件事**，并且**仍然被原文支持**。

**为什么需要**：**这是最容易被忽略、也最关键的一环。**

改写最容易出的问题是"**改完之后意思变了**"。而一个改变了原意的"降重"
比不降更糟 —— 它制造了一个**与事实不符的表述**，正好是本项目要防的事。

做法是**回接 E2 的证据层**：改写后的句子仍然是一条"断言"，
可以用同一套证据绑定与支持判断来验证它。

**如果保真校验不通过**：该条改写**不能采用**，如实报告"改写未被采用
（原因：改写后不再被原文支持）"。

### ⑥ 降重效果度量 `effect.py` ★

**作用**：用数字回答"**这次改写到底降低了多少重复**"。

**为什么需要**：**降重不能靠"感觉换了个说法"。**

没有度量会有两个后果：
- 无法判断改写是否有效，**也无法重试**；
- 报告里给不出任何依据，用户只能盲信。

度量用 `00-core/overlap` 的两个互补指标：

| 指标 | 回答 | 为什么需要它 |
|---|---|---|
| **最长连续重叠** | 还剩多长一字不差的连续片段？ | 直接反映"照搬" |
| **n-gram 包含率** | 新句子里有多少词组来自原句？ | **防住"把长句拆成短句"这种假改写** |

**两个都低才算改写成功。** 只看一个会被骗：拆句能压低连续重叠，
但词组还是抄的（这条在 `00-core/tests/test_overlap.py` 里有专门测试）。

**改写-度量-重试循环**：一次不达标就重试（换策略或换提示），
最多 N 次；仍不达标则**如实报告"未能达标"**，不假装成功。

### ⑦ 降重报告 `report.py`

**作用**：原文 / 改写 / 效果数字 / 保真结论 **四栏对照**。

**为什么需要**：用户需要能**自己判断改得对不对**。
只给一个"已降重"的结论，用户无从核对 —— 而改写是**用户的论文**，
最终责任在他身上，他必须能看懂系统改了什么。

# 第二部分：设计路线与验收

## 设计路线（实施步骤）

| 步 | 内容 | 产出 |
|---|---|---|
| 1 | 改写单元切分 | `units.py` |
| 2 | 受保护片段识别 | `protected.py` ✅ 已就位 |
| 3 | 重叠度量接好 | 复用 `00-core/overlap.py` ✅ 已就位 |
| 4 | 保真校验（接 E2） | `fidelity.py` |
| 5 | 改写策略 | `strategy.py` |
| 6 | 改写生成接口 + stub 实现 | `rewriter.py` |
| 7 | 改写-度量-重试循环 | `pipeline.py` |
| 8 | 报告 + 端到端样例 | `report.py` / `examples/` |

## 验收标准

1. **逐字复制的段落** → 改写后重叠**显著下降**，并且报告里给出**具体数字**；
2. **受保护片段**（引号内 / 带引用标注 / 术语 / 数据）→ **不被改写**，
   并说明原因；定义类内容 → 给出「建议规范引用」而不是改写建议；
3. **改写后语义保真** → 通过 E2 的证据校验；**不通过的不采用**；
4. **改写不足以降重** → 如实报告"未能达标"，**不假装成功**；
5. **没有模型时全链路可跑通**（用 stub rewriter），测试不被阻塞；
6. 代理指标（情况 B）必须在报告里**标注为代理**，不当成真实降重率。

## 关键设计判断

| 判断 | 理由 |
|---|---|
| **保真校验不可省** | 改了意思的"降重"比不降更糟：它制造了一个与事实不符的表述 |
| **不自动替换原文** | 与 E1 同理：改写涉及用户意图，只给建议 |
| **有来源就按来源度量，没有就诚实标注代理** | 拿代理指标冒充真实降重率是欺骗 |
| **改写生成做成可插拔接口** | 没模型能跑通、换模型不改代码、不同模型可做对照 |
| **度量必须有两个指标** | 拆句能骗过连续重叠，但骗不过 n-gram 包含率 |
| **定义类内容建议引用而非改写** | 硬改定义会既不准确又不像原文，比重复率高的危害更大 |
| **重试有上限，超限如实报告** | 无上限重试会烧钱，而且掩盖"这段本来就改不动"这个事实 |

## 与其他模块的关系

| 模块 | 关系 |
|---|---|
| **E3 报告解析** | **上游**：提供已定位的重复片段 |
| **E2 引用真实性** | **复用**其证据校验做保真校验；复用其引用识别做受保护片段 |
| **E5 降AI** | **共享改写框架**（生成接口、保真校验流程），只是策略不同 |
| **00-core / overlap** | **复用**其重叠度量（这正是它存在的理由） |

# 第三部分：实现细节

## ① 改写单元 `units.py`

按句切分 + **合并过短的句子**：

```python
if (cur_end - cur_start) < min_chars:
    cur_end = end          # 太短 → 与下一句合并
```

**为什么不单独改短句**：一个 5 字的句子（「因此。」）没有改写空间，
强行改只会变成同义词替换 —— 那是最典型的**伪改写**。

受保护判定在这里就做，复用 E2/E3 的 `citation_status`。

## ② 受保护片段 `protected.py`（从 E3 迁移）

判定：**引号内** 或 **所在句含引用标注**。

**★ 为什么用「所在句」而不是「所在段」**：一段话里可能既有引用别人的地方，
也有自己的原创表述。按段判定会把整段都保护起来，**漏掉真正该改的部分**。

**`《》` 刻意不算引号**：它是书名号，标记作品名。把它当引号会放过
「整段抄一本书」—— 那是最该被改写的部分。

## ③ 策略选择 `strategy.py`

分类顺序**有意义**：

```python
DEFINITION → DATA → METHOD → CONCLUSION → OTHER
```

**为什么 METHOD 排在 CONCLUSION 之前**（实测调整过）：
「本文提出了一种…方法，并在…验证了效果」同时命中两边，
但它的**主要信息是方法**，改写时应保留术语、改句式。

**为什么 `_METHOD` 里删掉了 `该方法|本方法`**：这两个词太泛，
结论句里也常见（「结果表明该方法…」），保留它们会把结论误判成方法。

**数据阈值 0.18 刻意留得较高**：像「结果表明…提升了 8.3%」这样的句子
仍按结论处理 —— 其中的数字由**保真校验**守住，不必整句禁改。

## ④ 改写器 `rewriter.py`

```python
class Rewriter(Protocol):
    name: str
    def rewrite(self, request: RewriteRequest) -> list[str]: ...
```

三个实现：`StubRewriter`（原样返回）、`CannedRewriter`（预设映射）、
`CallableRewriter`（包函数）。

**`CannedRewriter` 用归一化匹配键**（去空白、去首尾标点）：

**为什么不用原始字符串匹配**（实测踩过）：改写单元按句切分，
**句末标点常被裁掉**，用原始串匹配会莫名对不上。

## ⑤ 保真校验 `fidelity.py` ★

四项确定性检查：

| 检查 | 抓什么 |
|---|---|
| **数字保留** | 吞掉数字 / 编造数字 |
| **结论级否定** | 把结论说反 |
| **长度合理** | 删掉内容（<50%）/ 加进内容（>200%） |
| **专名保留** | 丢失 `BERT`、`《书名》` |

**★ 为什么不用通用的 `has_negation`**（实测踩过）：
它匹配任何「不/没/未」，于是「**不到**一百行」这种普通表述
也会被当成"否定被翻转"，把**正常的改写误判成失真**，
大量可用候选被白白拒掉。

改成只认**结论级否定**：

```python
_VERDICT_NEGATION = re.compile(
    r"并不|并未|未能|不能|不会|不可|无法|不足以|不属于|不存在|尚无|缺乏"
    r"|没有(?:提升|改善|差异|效果|优势)"
)
```

## ⑥ 效果度量 `effect.py` ★

```
suspicion 不适用；这里用：
after_run         改写后与原句/来源的最长连续重叠
after_containment n-gram 包含率
meets_target = after_run <= 12 且 after_containment <= 0.35
```

**两个都要**：只看连续重叠会被「拆短句」骗过 —— 拆开之后连续段变短了，
但词组还是抄的（`00-core/tests/test_overlap.py` 有专门验证）。

**直接度量 vs 代理指标**：

```python
if source_text:  measured_against = "source"    # 直接度量
else:            measured_against = "original"  # 代理指标
```

代理指标在 `summary()` 里**明确标注**，报告原样写出 ——
不把代理指标冒充成真实降重率。

## ⑦ 流水线 `pipeline.py`

**判定顺序：先保真，再效果**

```python
if not fidelity.ok:
    fidelity_failed.append(fidelity)
    continue                     # ← 保真是否决条件
if effect.meets_target:
    return accepted
rejected.append(...)             # ← 保真但没降够，可重试
```

**这个顺序不能反** —— 反过来会出现"为了降重而牺牲准确"的产出。

# 第四部分：实测结果

演示：`python 06-revise/f2-rewrite/examples/demo_rewrite.py`

⚠️ **改写候选是人手写的**（`CannedRewriter`），真实使用时由模型生成。
下面的数字演示的是**链路在拿到好候选时的行为**，不代表模型能力。

## ① 好改写 → 采纳

| 项 | 值 |
|---|---|
| 原文 | 本文提出了一种基于图神经网络的推荐方法，并在三个数据集上验证了效果 |
| 改写 | 我们的方案借助图结构对用户与物品的关联建模，在三个公开数据集上完成了评估 |
| 内容类型 | 方法描述 |
| 策略 | rephrase |
| **最长连续重叠** | **4 字**（达标线 12） |
| **n-gram 包含率** | **0%**（达标线 35%） |
| 保真 | 通过（数字/否定/长度/专名四项） |

## ② 四种"不该改"的情况

| 情况 | 状态 | 说明 |
|---|---|---|
| 引号内的引用 | 🔒 引用豁免 | 位于引号内（直接引用） |
| 定义类表述 | 📌 建议改为引用 | 硬改定义会失准 |
| 纯数据句 | 🔒 数据不改 | 数字不能改，改了就是伪造数据 |
| 改写丢数字 | ❌ 保真未通过 | 已弃用 —— 丢失了数字 8.3%、12.5% |

## ③ 没有模型时

`StubRewriter` 原样返回 → 效果度量显示"没改善" → 走「未达标」分支，
报告写「请人工改写这一段」。

**这正好把失败路径也测到了** —— 比返回一个"看起来更好"的假改写有用得多。

# 第五部分：已知局限

| 局限 | 说明 |
|---|---|
| **改写必须用模型** | 这是 E 阶段唯一不能确定性实现的一环。当前只有 stub 与预设映射 |
| **不做完整语义等价判断** | 保真校验能抓最常见的失真（吞数字、翻转否定、丢专名），但抓不住「表述完全变了但字面都合规」 |
| **代理指标不等于真实降重率** | 报告未给来源原文时，只能以用户原句为基准 —— 已在报告里标注 |
| **重试只对随机性改写器有意义** | 确定性改写器重试结果相同 |
| **策略分类靠关键词** | 「结果表明该方法…」这类混合句可能被判成方法描述；不过数字由保真守住，影响有限 |
| **定义类只给建议不给改写** | 这是刻意的：硬改定义会既不准确又不像原文 |

# 第六部分：真实模型接入

> 代码：`llm.py`（`LlmRewriter`）· 底层：`00-core/src/copilot/llm.py`
> 演示：`python examples/demo_llm_rewrite.py`（`--dry-run` 只看提示词不花钱）

## 一、怎么接上的

三条原则决定了实现方式：

**① 只实现 `Rewriter` 协议，其余代码一行不改**

```python
class Rewriter(Protocol):
    name: str
    def rewrite(self, request: RewriteRequest) -> list[str]: ...
```

`LlmRewriter` 只是第四个实现（前三个是 `StubRewriter` / `CannedRewriter` / `CallableRewriter`）。
**流水线、保真校验、效果度量、报告全都不用改** —— 这就是当初留接口的回报。

**② E5 直接复用，不另写一套**

`from copilot.quality.rewrite import LlmRewriter` —— E5 只是换了个「改写要求」，
提示词骨架完全共用。

**③ 没密钥时优雅退化**

`LlmConfig.from_env()` 抛 `LlmError` → 演示脚本打印"跳过"并返回 0。
整条链路仍可用 `StubRewriter` 跑通。

## 二、提示词：把不可动的部分列死

系统提示里五条硬约束，**每一条都对应 `fidelity.py` 的一个检查项**：

| 提示词说的 | 对应校验 |
|---|---|
| 不得新增数字 / 实验条件 / 文献 | `number`：编造数字会被抓 |
| 保留数字、单位、专名、引用标注 | `number` + `term` |
| 不得改变原意，限定条件不能丢 | `negation` |
| 字数 0.8–1.2 倍 | `length` |
| 只输出正文 | （清洗环节处理） |

**★ 提示词与校验器说同一件事，模型才知道边界在哪。**

**但提示词是软约束，校验器才是硬闸门** —— 即使模型不听话，
`check_fidelity` 也会把它拦下来。这个分工很重要：
把质量寄托在提示词上是不设防的。

## 三、★ 通过率评测：3 个配置的对照实验

> 脚本：`eval/run_rewrite_eval.py` · 报告：`reports/rewrite_pass_rate.md`
> 模型：`gpt-6.1-sol` · 规模：**6 片段 × 2 次重复 × 3 配置 = 36 个任务**

### 先量化基线：单次调用只有 42%

第一次接真实模型时看到的"约 50% 通过率"不是错觉。正式测下来：

| 配置 | 说明 | 通过 | 通过率 | 平均耗时 |
|---|---|---|---:|---:|
| **A** | v1 提示词 + 单次 | 5/12 | **42%** | 14.0s |
| **B** | v2 提示词 + 单次（只改提示词） | 10/12 | **83%** | 24.6s |
| **C** | v2 提示词 + 重试 3 次 | 12/12 | **100%** | 17.4s |

### 配对检验（McNemar + bootstrap CI）

| 比较 | 通过率 | Δ (95% CI) | 翻转 (b/c) | p | 结论 |
|---|---|---|---:|---:|---|
| A → B（提示词） | 42% → 83% | +42% [+0%, +75%] | 1/6 | 0.1250 | 方向明确，**不显著** |
| B → C（重试） | 83% → 100% | +17% [+0%, +42%] | 0/2 | 0.5000 | 不显著 |
| **A → C（合计）** | **42% → 100%** | **+58% [+33%, +83%]** | **0/7** | **0.0156** | **显著提升** |

**怎么读这个结果**：

- **合计显著**（CI 下界 +33%，p=0.016）—— 两个手段一起用，通过率确实从 42% 提到 100%；
- **单看每一步都不显著** —— 提示词单独 6 次翻转（p=0.125），重试单独 2 次翻转（p=0.5）。
  这不是"没用"，而是**样本量（12 个任务）不足以分辨单步效应**。

这正是配对检验该有的样子：**结论与样本量匹配**，而不是"看起来改善很大就宣布胜利"。

### ★ 一个意外的好消息：保真一次都没被触发

36 个任务里，**所有失败都是 `rejected_effect`，`rejected_fidelity` 为 0**。

意思是：模型**从来没有改坏事实**（没编数字、没翻否定、没丢专名）——
它的问题只是"改得不够远"。

这说明**提示词里的五条硬约束是有效的**：模型知道哪些不能动。
真正的瓶颈在"怎么改得更彻底"，而不在"会不会改坏"。

这个区分很重要：如果失败是保真类，要改的是**约束**；
既然失败是效果类，要改的是**结构引导**。

### 为什么 v2 有效

v1 只说"改写表达方式"，模型于是做**同义替换** —— 句子骨架不变，
连续重叠 12~21 字，包含率 43%~76%。

v2 追加了一段结构要求：

> 不要只替换同义词 —— 那只算润色，不算改写。必须改变句子结构：
> 调整语序 / 换主语视角 / 拆分合并 / 改变分句连接方式。
> **目标：不要有任何连续 10 个字以上与原文相同。**

**关键**：这句话给了模型一个**可核对的量化靶子**，
而且这个数字（10 字）与 `effect.py` 的达标线（12 字）方向一致。
**提示词与度量说同一件事，模型才不是盲猜。**

效果：包含率从 43%~76% 降到 2%~26%。

### 最难的一个片段

片段 5（`针对长尾用户的行为稀疏问题，本文引入了一种基于元学习的冷启动方案。`）
在 A 配置下包含率 **76%**，是唯一在 B 配置下也失败过一次的片段。

原因很直接：这句话**几乎没有可替换的表达** ——
"长尾用户""行为稀疏""元学习""冷启动"都是必须保留的术语，
剩下的虚词不足以支撑结构重组。

> 这提示一个**结构性限制**：术语密度极高的句子，
> 降重空间本身就很窄 —— 再好的提示词也改不动。
> 这类句子更适合**建议引用**（`Strategy.CITE_INSTEAD`）而不是硬改。

## 四、★ 两个实测发现

### 发现 1：这个端点**不支持 `n` 参数**

请求 3 个候选，服务端**只返回 1 个，而且不报错**。

后果很隐蔽：调用方以为"我拿 3 个候选挑最好的"，
实际上一直在拿 1 个 —— **多候选根本没生效，而且看不出来**。

修法：`LlmRewriter` 用 `n_ignored` 计数，`stats()` 暴露出来。

```python
st = rewriter.stats()
# {'calls': 4, 'n_candidates': 3, 'n_ignored': 4, 'n_supported': False}
```

演示脚本发现后直接打印：

> ⚠️ 该端点**不支持 n 参数**。所以提高通过率要靠 `max_attempts` 重试，而不是多候选。

**结论**：真正的杠杆是**重采样（多次调用）**，不是一次要多个候选。
`run_rewrite(..., max_attempts=N)` 就是干这个的。

### 发现 2：单次调用质量方差很大

同一输入、同一温度（0.3），四次结果从「只换了两个字」到「大幅重组句式」都有，
重叠字数在 **7–21 字**之间摆动。

这不是 bug，是语言模型的正常方差 —— 但它意味着：

> **不能拿一次结果下结论。**
> 评价改写器能力，必须跑多次取分布，而不是挑一次好看的。

这与项目第二条原则（必须有对照组）是同一件事：
**单次样本不能支撑结论，哪怕结论看起来很好。**

## 五、E5 同款接入

```python
from copilot.quality.deai import run_deai
from copilot.quality.rewrite import LlmRewriter

report = run_deai(checklist, rewriter=LlmRewriter(cfg))
```

E5 的 `verification` 会给出特征前后对比，例如实测：

```
⚪ sentence_length_cv 0.000 → 0.000 =
⚪ transition_density 0.000 → 0.000 =
✅ specificity        0.000 → 3.448 ↑
⚪ parallelism        0.000 → 0.000 =
```

**⚠️ 这里暴露了 E5 的一个 bug（已修）**：
`specificity` 从 0 跳到 3.448 是**假提升** —— 模型的改写里多了个「进一步」，
而 `_CN_NUMBER` 把「进一步」匹配成了「一步」（`步` 在量词表里），
于是一个纯 idiom 被算成了"具体信息点"。

修法：计数前剔除 idiom（`_CN_NUMBER_IDIOMS`），并加了三条测试锁住。

> 这个 bug **只有接真实模型才会暴露** —— 人造夹具里没人会写「进一步」。
> 它说明一件事：**接真模型不只是"能用"，它还是一个更强的测试。**

## 六、已知局限

| 局限 | 说明 |
|---|---|
| **单次通过率约 50%** | 需要 `max_attempts` 重试；当前默认 2 次，实际可能不够 |
| **`n` 参数不可用** | 该端点忽略 `n`，多候选策略失效 |
| 串行调用很慢 | 单次 10–30 秒；批量改写没有并发 |
| 无 token 成本统计 | 只知道调用次数，不知道花了多少 |
| 提示词未做 A/B | 五条硬约束是设计出来的，**没有对照实验证明哪条最有效** |
| 只在 1 个模型上验证过 | 换模型效果未知 |
