## 本模块解决的核心问题

> **外部 AI 检测报告指出了哪些段落"像 AI 写的"，把这些段落的表达改得更像人写的 —— 同时不改变原意。**

**本模块不做 AI 检测。** 输入是 E3 解析定位好的问题清单。

# 第一部分：设计

## ★ 与 E4 的根本差别：**没有"对方"可比**

这是本模块设计上最需要注意的一点：

| | E4 降重 | E5 降AI |
|---|---|---|
| 要降低什么 | 与**某个出处**的文字重叠 | **风格特征**的"机器味" |
| 有明确的比对对象吗 | **有**（来源原文或用户原句） | **没有** —— 不存在"AI 原文" |
| 怎么验证有效 | 重叠度下降（可测量） | 风格特征是否向目标移动（可测量） |
| 怎么验证没改坏 | 证据保真（接 E2） | **同样**是证据保真（接 E2） |

**"没有比对对象"意味着**：不能像 E4 那样简单地对两段文字量重叠。
必须先把"AI 味"拆成**可测量的客观特征**，改写后重新测这些特征。

## ★ 必须先说清楚的一件事：什么叫"像 AI 写的"

**"这段文字是不是 AI 生成的"是一个不可靠的推断** —— 现有检测器的
准确率与误报率都达不到可以据处分的程度。本模块**不对此做任何判断**。

本模块处理的是**报告说了什么**（外部工具的结论，由用户负责），
以及**可测量的风格特征**：

| 特征 | 为什么可测 | "AI 味"的常见表现 |
|---|---|---|
| **句长分布** | 直接可算 | 过于均匀（方差小） |
| **连接词密度** | 可枚举统计 | "此外/然而/综上所述/值得注意的是"偏多 |
| **排比与对仗** | 结构模式可匹配 | 工整的"首先…其次…最后…" |
| **词汇丰富度** | 可算 TTR | 用词重复或过于"标准" |
| **具体性** | 数字/专有名词密度 | 缺少具体细节，多是泛泛而谈 |
| **段落长度分布** | 直接可算 | 各段长短过于接近 |

**这些是客观可测的量，不是身份推断。** 本模块只报告特征的**变化**，
不声称"改完就不是 AI 写的了"。

## 六个子部分：作用与「为什么需要」

### ① 风格特征提取 `features.py`

**作用**：把"AI 味"变成一组**可计算的数字**。

**为什么需要**：**不可测量的东西无法改进，也无法验证。**
如果只说"这段读起来像 AI"，改写就没有目标，改完也无法判断有没有改善。

这与 E4 需要 `overlap` 是同一条理由：**每一步改进都要有可测量的判据。**

### ② 异常定位 `diagnose.py`

**作用**：对报告指出的片段，**具体诊断它哪一项特征异常**。

**为什么需要**：**"疑似 AI"不是一个可执行的指令。**
"套话连接词太多"和"句长过于均匀"需要**完全不同的改写方向**：
- 前者要**删连接词**；
- 后者要**打散句式、长短交错**。

不诊断就直接让模型"改得像人一点"，产出的往往是同义词替换式的伪改写。

**刻意的范围限制**：只诊断**报告指出的**片段，不做全文扫描定性。
理由是"判断哪段像 AI"是外部工具的职责，本模块越界只会重复那个不可靠的推断。

### ③ 改写策略 `strategy.py`

**作用**：把诊断结果映射成具体的改写指令。

**为什么需要**：策略与诊断一一对应，才能保证"改的是问题所在"：

| 诊断 | 策略 |
|---|---|
| 句长过于均匀 | 长短句交错，适度拆分或合并 |
| 套话连接词偏多 | 删减或替换为具体逻辑连接 |
| 缺少具体细节 | 提示补充数字、条件、例子（**但不能编造**） |
| 排比过于工整 | 打破结构对称 |

**★ "补充具体细节"必须有严格约束**：模型**不能编造数据**。
只能提示用户"这里可以补充具体的实验条件/数值"，
或者从上下文中已有的信息里提取。编造数据的危害远大于"AI 味"。

### ④ 改写生成

**作用**：调用模型产出改写。

**为什么需要**：与 E4 同理，规则做不到真正的重述。

**关键设计：复用 E4 的 `Rewriter` 接口，不另起一套。**

```
E4 的 generate 阶段  ─┐
                      ├─→ 同一个 Rewriter 接口 → 不同策略 → 不同目标
E5 的 generate 阶段  ─┘
```

**为什么复用**：两者的**流程完全相同**（切分 → 保护 → 策略 → 生成 → 校验 → 重试），
只有"策略"与"校验目标"不同。实现两遍意味着两处都要维护重试逻辑、
错误处理、模型适配 —— 而它们必须保持一致。

### ⑤ 风格与保真双校验 `verify.py` ★

**作用**：改写后做**两项**检查，都通过才采用。

| 校验 | 回答 | 不通过怎么办 |
|---|---|---|
| **风格校验** | 目标特征是否真的改善了？ | 不达标 → 重试或如实报告"未能改善" |
| **保真校验** | 是否仍被原文支持？（接 E2） | 不通过 → **直接弃用** |

**为什么两项都要**：
- 只做风格校验 → 改得"像人写的"但**意思变了**，这是最坏的结果；
- 只做保真校验 → 什么都没改也能通过（保真当然通过）。

**保真优先于风格**：两者冲突时，宁可不改，也不能改动原意。
这与 E4 的「定义类内容建议引用而非改写」是同一条原则 ——
**准确性的优先级永远高于降 AI。**

### ⑥ 报告 `report.py`

**作用**：原文 / 改写 / **特征前后对比** / 保真结论。

**为什么需要**：
- 用户需要看到"**哪些特征变了、变了多少**"，而不是一句"已降 AI"；
- 必须写明**本模块不做身份判断** —— 报告不能被误用为"证明这不是 AI 写的"。

# 第二部分：设计路线与验收

## 设计路线（实施步骤）

| 步 | 内容 | 产出 |
|---|---|---|
| 1 | 风格特征提取 | `features.py` |
| 2 | 异常诊断 | `diagnose.py` |
| 3 | 改写策略映射 | `strategy.py` |
| 4 | 复用 E4 的 `Rewriter` 接口 | （依赖 E4 先完成） |
| 5 | 风格 + 保真双校验 | `verify.py` |
| 6 | 报告 + 端到端样例 | `report.py` / `examples/` |

**依赖**：本模块**必须在 E4 之后做** —— 它复用 E4 的改写框架与校验流程。
先做 E4 可以把框架打磨好，E5 直接接上，避免两个模块各写一套重试逻辑。

## 验收标准

1. **特征可测**：给定一段文字，能算出句长方差、连接词密度、词汇丰富度等，
   且数值可复核（手工能算出来）；
2. **诊断可解释**：能说清"这段的问题是连接词密度 3.2 倍于全文均值"，
   而不是"这段像 AI"；
3. **改写后特征有改善**：给出**前后对比数字**，而不是结论；
4. **保真校验优先**：改写后若不再被原文支持 → **弃用**，即使风格改善明显；
5. **不编造细节**：策略中"补充具体细节"**不得生成不存在的数据**；
6. **不做身份判断**：报告里不出现"这段是/不是 AI 写的"这类断言。

## 关键设计判断

| 判断 | 理由 |
|---|---|
| **只处理报告指出的片段** | "哪段像 AI"是外部工具的职责；本模块越界只会重做那个不可靠的推断 |
| **把"AI 味"拆成可测特征** | 不可测量的东西无法改进，也无法验证 |
| **先诊断再改写** | "改得像人一点"不是可执行指令；不同病因需要不同改法 |
| **复用 E4 的改写框架** | 流程完全相同（切分/保护/生成/校验/重试），实现两遍必然会不一致 |
| **保真优先于风格** | 冲突时宁可不改 —— 准确性高于降 AI |
| **补充细节不得编造** | 编造数据的危害远大于"AI 味" |
| **报告不做身份判断** | 检测本身不可靠，报告不能被误用为依据 |

## 与其他模块的关系

| 模块 | 关系 |
|---|---|
| **E3 报告解析** | **上游**：提供已定位的"疑似 AI"片段 |
| **E4 降重** | **共享改写框架**（`Rewriter` 接口、重试逻辑、报告结构） |
| **E2 引用真实性** | **复用**其证据校验做保真校验 |
| **00-core / stats** | 特征对比若要做显著性判断，复用配对检验工具 |

## 与 E4 的共用边界（实现时的约定）

```
                共用                          各自独有
   ┌──────────────────────────────┐   ┌────────────────────┐
   │ Rewriter 接口（模型接入）      │   │ E4: 重叠度量        │
   │ 受保护片段识别（protected.py） │   │ E5: 风格特征        │
   │ 保真校验流程（接 E2）          │   │ E4: 降重策略        │
   │ 改写-校验-重试循环            │   │ E5: 降AI策略        │
   │ 报告骨架                     │   │ E4: 来源原文处理     │
   └──────────────────────────────┘   └────────────────────┘
```

**判断标准**：如果一段代码在 E4 和 E5 里长得一样，它就该在共用部分。

# 第三部分：实现细节

## ① 风格特征 `features.py`

六个特征，全部**直接可复核**（同一段文字，任何人算出来都一致）：

| 特征 | 怎么算 | "AI 味"的表现 |
|---|---|---|
| `sentence_length_cv` | 句长标准差 / 均值 | **越小越均匀** |
| `transition_density` | 套话连接词数 / 句数 | 偏多 |
| `lexical_diversity` | 二字组 TTR | 参考项 |
| `specificity` | (数字 + 专名 + 书名) / 百字 | 偏低 |
| `parallelism` | 排比框架数 / 千字 | 偏多 |

**为什么用变异系数（CV）而不是标准差**：长短段落的绝对差异无法跨文本比较，
用相对差异才能判断"是不是过于均匀"。

**★ 中文数字必须数进去**（实测踩过）：只数阿拉伯数字时，
「**两个**真实业务场景」「不到**一百**行」这类**完全正常的真人写作**
会被判为"缺少具体信息"，于是系统会去硬改本来就好的文字。

```python
_CN_NUMBER = re.compile(
    r"[一二三四五六七八九十百千万两半几]+\s*"
    r"(?:个|次|年|月|日|倍|成|种|类|项|条|行|步|轮|层|维|组|篇|页|章|节|位|名)"
)
```

## ② 诊断 `diagnose.py`

四个绝对阈值（都可配置）：

```python
CV_LOW           = 0.35   # 句长变异系数低于此值 → 句式过于均匀
TRANSITION_HIGH  = 0.55   # 每句套话连接词数高于此值 → 偏多
SPECIFICITY_LOW  = 0.8    # 每百字具体信息点低于此值 → 泛泛而谈
PARALLELISM_HIGH = 0.5    # 每千字排比框架数高于此值 → 过工整
```

每条诊断都带**具体数字**：

> 句长变异系数只有 0.00（低于 0.35），句子长度过于整齐

**为什么不用机器学习判"像不像 AI"**：那是不可靠推断。
阈值是**可复核的判断标准** —— 用户能自己算一遍核对。

## ③ 策略 `strategy.py`

诊断 → 策略一一对应：

| 诊断特征 | 策略 |
|---|---|
| `sentence_length_cv` | 打散句式 |
| `transition_density` | 删减连接词 |
| `specificity` | 补充具体信息 |
| `parallelism` | 打破排比 |

多条诊断合成一条指令（一次改写同时处理多个病因），
因为分多次改写既费钱，又容易产生风格断裂。

**★ `ADD_SPECIFICS` 的硬约束**（写在提示词里）：

> 使用原文与上下文里**已经存在的**数字、条件、方法名称。
> **绝对不要编造任何数据、数值或事实。**

## ④ ★ 为什么 E5 不能复用 E4 的单句切分（`units.py`）

这是本模块**最重要的一处设计修正**。

E4 按**句**改写是合理的：重复以句子为单位。
但 E5 的目标特征本身**是跨句的**：

- **句长变异系数** —— 一句话没有"方差"可言；
- **连接词密度** —— 需要多句才看得出密度；
- **排比/对仗** —— 「首先…其次…最后」跨句成立。

**实测踩过的现象**：用单句切分时，**每个单元都被诊断出"句式过于均匀"**，
但那是**切分方式造成的假象**，不是文本的问题。

因此 E5 用**段落级单元**：

```python
DEFAULT_MIN_SENTENCES = 2    # 少于 2 句谈不上"句式变化"
DEFAULT_MAX_CHARS = 400
```

最后一段若不足 2 句，**并入前一段** —— 避免产出"单句单元"。

## ⑤ 双校验 `verify.py` ★

```python
def ok(self):
    return self.fidelity_ok and self.style_improved
```

**为什么两项都要**：

| 只做其中一项 | 结果 |
|---|---|
| 只做风格校验 | 改得"像人写的"但**意思变了** —— 最坏 |
| 只做保真校验 | **什么都没改也能通过** |
| **两项都做** | ✅ |

**冲突时保真优先**：宁可不改，也不能改动原意。

**"改善"的判定**：

```python
MIN_IMPROVEMENT = 0.10    # 相对变化至少 10% 才算改善
```

太小的变化没有实际意义 —— 那只是措辞抖动，不是风格改变。

**只要目标特征里**有一项**改善即可**（不要求全部）：
一次改写通常只能改善一两个维度，要求全部会把大量可用候选拒掉。

# 第四部分：实测结果

演示：`python 06-revise/f2-rewrite/examples/demo_deai.py`
报告：`reports/deai_report.md`

⚠️ 改写候选是人手写的（`CannedRewriter`），演示链路行为，不代表模型能力。

## 特征对比（实测数值）

| 文本 | 句长变异系数 | 连接词密度 | 具体性 | 排比 |
|---|---:|---:|---:|---:|
| **机器味片段** | **0.00** | **1.00** | **0.00** | **22.73** |
| 正常片段 | 0.69 | 0.00 | 4.17 | 0.00 |

机器味片段的四个指标全部落在阈值外 —— 诊断出四项问题。

## 好改写 → 采纳后的特征变化

```
✅ sentence_length_cv  0.000 → 0.739 ↑
✅ transition_density  1.000 → 0.000 ↓
⚪ specificity         0.000 → 0.000 =
✅ parallelism        22.727 → 0.000 ↓
```

保真：通过（数字/否定/长度/专名四项）

## 编造数字 → 拦下

| 项 | 内容 |
|---|---|
| 候选 | 该方法有效。在 37 个数据集上准确率达到 94.2%。实现简单。 |
| 状态 | ❌ 保真未通过 |
| 说明 | 改写后出现了原文没有的数字：37, 94.2% |

**这是刻意的**：「补充具体信息」只能用手上**已有**的信息。
编造数据的危害远大于 AI 味 —— 一段风格差的内容只是风格问题，
一段编造的实验数据是学术不端。

## 风格正常 → 不改

「我们在两个真实业务场景里跑过…」被判为**无需改写**（`no_diagnosis`）——
不为"降 AI"去硬改正常文字。

# 第五部分：已知局限

| 局限 | 说明 |
|---|---|
| **改写必须用模型** | 与 E4 相同，当前只有 stub 与预设映射 |
| **不做 AI 检测** | 只处理外部报告指出的片段，不对"是不是 AI 写的"下结论 |
| **阈值是经验值** | 四个阈值无标注数据支撑，属先验设定 |
| **"改善"不等于"检测分数会降低"** | 外部工具怎么打分是它的事，本系统不预测 |
| **补全具体信息受保真约束** | 原文没有的数字不能加 —— 所以"提高具体性"这条往往改不动 |
| **词汇丰富度只做参考** | 二字组 TTR 是近似指标，不做判定 |

# 第六部分：真实模型接入与一个只有它能暴露的 bug

## 接入方式

E5 直接复用 E4 的 `LlmRewriter`，**一行都不用自己写**：

```python
from copilot.quality.deai import run_deai
from copilot.quality.rewrite import LlmRewriter

report = run_deai(checklist, rewriter=LlmRewriter(cfg))
```

理由：E5 与 E4 的差别只在**策略**（改什么特征），不在**怎么让模型改写**。
提示词骨架、输出清洗、候选过滤三者完全共用。

## 实测：4 次里 2 次 accepted

同一段输入（`该方法在低资源场景下仍有提升空间。`）跑了多次：

| 结果 | 特征变化 |
|---|---|
| ✅ accepted | `specificity 0.000 → 3.448 ↑`（**这个数字是假的，见下**） |
| ❌ rejected_style | 改写后目标特征没有改善 |

**单次不可靠**这一点与 E4 相同 —— 两处都靠 `max_attempts` 重采样。

## ★ 一个只有接真实模型才会暴露的 bug

那次 `specificity 0.000 → 3.448` 看起来是"具体性提升了"，实际上是**假提升**。

复现步骤：

```
原文  ：该方法在低资源场景下仍有提升空间。        specificity = 0.000
改写后：实验结果表明，该方法在低资源场景下仍存在进一步提升的空间。  specificity = 3.448
```

改写里只多了一个词：**「进一步」**。

### 根因

`_CN_NUMBER` 是"中文数字 + 量词"的正则：

```python
r"[一二三四五六七八九十百千万两半几]+\s*(?:个|次|…|步|…)"
```

`步` 在量词表里，于是**「进一步」被匹配成了「一步」** ——
一个纯 idiom 被当成了"具体信息点"。

### 为什么这个 bug 危害不小

`specificity` 偏低是"AI 味"的一个诊断信号。
虚高会让**本该被判"缺少具体信息"的段落逃过诊断** ——
系统不再建议补充细节，而这正是降 AI 最有效的手段之一。

### 修法

计数前剔除 idiom：

```python
_CN_NUMBER_IDIOMS = ("进一步", "进一步地", "第一步")

def _count_cn_numbers(text):
    for idiom in _CN_NUMBER_IDIOMS:
        text = text.replace(idiom, "")
    return len(_CN_NUMBER.findall(text))
```

加三条测试锁住：idiom 不计入、带 idiom 的泛泛表述仍被判低具体性、
真实数量（三个数据集 / 两步处理）仍要数进去。

> **为什么人造夹具永远测不出来**：没人会在测试里写"进一步"。
> 它说明一件事 —— **接真模型不只是"能用"，它还是一个更强的测试。**

## 已知局限

| 局限 | 说明 |
|---|---|
| 单次通过率不稳定 | 4 次里 2 次达标，需要重试 |
| idiom 黑名单是手工维护的 | 「更进一步」「进一步地」之外还有别的固定说法，可能还有漏网的 |
| 特征只是**代理指标** | 外部工具怎么打分是它的事，本系统不预测 |
| 只在 1 个模型上验证过 | 换模型效果未知 |
