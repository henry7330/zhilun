# 第一部分：设计

## 1.1 这个 Agent 解决什么问题

外部查重/AI 检测工具会给你一份报告，上面标着"这段重复了""这段像 AI 写的"。
**真正耗时的不是知道哪里有问题，而是把那些片段重写一遍。**

这个阶段就做这一件事：

```
外部报告 ──▶ 定位到文档里的具体位置 ──▶ 改写那个片段 ──▶ 校验改得对不对
```

## 1.2 边界：我们不做什么

| 不做 | 谁做 | 为什么 |
|---|---|---|
| 查重 / 测 AI 率 | **外部工具**（知网/维普/PaperPass/GPTZero） | 那是需要大规模语料比对的服务，不是一个本地系统该干的事 |
| 判断"降多少才合格" | 学校/期刊的规定 | 我们只负责"把它降下来"，合格线由规则定 |
| 全自动改完就交 | **人** | 改写是"改意思表达"，必须有人过一眼 |

## 1.4 三个子部分：作用 + 为什么需要

### ① F1 报告解析定位

**作用**：把外部报告的文本，变成"文档里第几行、第几个字符到第几个字符"。

**为什么需要**：
报告只说"这段重复"，不说"在第 12 行"。没有定位，改写就无从下手 ——
你总不能让模型改"某一段"。

**不做会怎样**：用户得自己把每一条问题片段去文档里搜一遍、复制出来，
再贴给系统。那这个阶段就没有存在的意义了。

**★ 三级定位，而不是二级**

| 级别 | 含义 | 处理 |
|---|---|---|
| 精确 | 报告原文在文档里逐字找到 | 直接改 |
| 模糊 | 找得到但不完全一致（文档改过一版） | **改，但标注置信度让人核对** |
| 未定位 | 完全找不到 | **交回用户，不猜位置** |

为什么要有"模糊"这一级：报告常常是几天前的，文档已经改过。
全都判"未定位"太浪费，全都当"精确"又会改错地方。
中间这一级是必要的。

### ② F2 合并改写

**作用**：对每个已定位的片段，产出**一版**同时满足降重与降AI的改写。

**为什么需要**：
这是本阶段最核心、也最容易做错的地方。见下一节。

**不做会怎样**：那就退化成"给点建议"，而建议本来满大街都是。

### ③ 保真校验（不是独立节点，但是独立职责）

**作用**：拦下"改完意思变了"的候选。

**为什么需要**：改写的第一性要求是**不能改坏**。
一句"降重达标但把 5 改成 8"的改写，比不改更糟。

**不做会怎样**：系统会为了达标而编造数字、丢掉专有名词、翻转否定 ——
而且它是"达标"的，看起来还很成功。

## 1.5 ★ 核心设计判断：为什么要合并，而不是分两次改

旧设计里降重（E4）与降AI（E5）是两条独立流水线。合并的理由不是"省事"：

**① 它们做的是同一件事。** 都是"改这段文字"，只是目标不同。

**② 分开会互相抵消。**

```
原文：  本文提出了一种基于图神经网络的推荐方法，并在五个数据集上验证了效果。

第 1 次（降重）：作者设计了一个两阶段框架，把图结构引入推荐建模，测试覆盖五个数据集。
                → 与原文拉开了字面距离 ✓

第 2 次（降AI）：该框架首先进行粗筛，其次进行精排，此外还引入了图结构信息。
                → 风格改了，但「该框架…首先…其次…此外」是典型 AI 腔，
                  而且和第 1 次的表达结构又被推回到模板句式
                → 降重的成果被部分抵消 ✗
```

**③ 合成一条指令反而更容易达标。** 因为在同一次生成里，
模型能同时看到两个约束，不会"改完一个再破坏另一个"。

### 合成后的校验顺序（顺序不能反）

```
保真 → 重合 → 风格
```

| 顺序 | 理由 |
|---|---|
| **保真优先** | 它是**否决条件**。改了意思的候选，效果再好也弃用 |
| 重合第二 | 降重的硬指标，最容易度量 |
| 风格第三 | 相对最"软"，但也必须过 |

**反过来会怎样**：先看效果，就会出现"为了降重牺牲准确"的系统 ——
而这正是市面上很多改写工具的问题。

## 1.6 设计路线（带顺序）

| 步 | 内容 | 产出 | 验收标准（可判定） |
|---|---|---|---|
| 1 | 报告解析 | `parse_report` | 纯文本 / JSON / HTML 三种格式都能读出条目；空报告抛 `ValueError` |
| 2 | 三级定位 | `locate` + `Checklist` | 片段一致 → 精确；文档改过 → 模糊 + 置信度；对不上 → 未定位且**不硬指位置** |
| 3 | 受保护判定 | `citation_status` | 引号内 / 含引用标注的句子 → 一律不改 |
| 4 | 合并指令 | `build_instruction` | 目标含 overlap+style 时，两段要求**同时**出现在一条指令里 |
| 5 | 双校验 | `revise_unit` | 保真不过 → 弃用；重合/风格未达标 → 重试；重试用尽 → 报"需人工" |
| 6 | 阶段编排 | `run_revise` | 无报告 → `ValueError`；节点顺序 F1→F2；单片段失败不影响其他 |

## 1.7 关键设计判断（速查）

| 决策 | 不这样做会怎样 |
|---|---|
| **没有外部报告就拒绝运行**（抛 `ValueError`） | "跳过"会被读成"检查过了没问题"——这是整套系统最想避免的失败模式 |
| **未定位的交回用户**，不猜位置 | 硬指一个位置会让用户改错地方，比不改更糟 |
| **模糊定位要标注置信度** | 用户无法判断"这条到底是不是真的" |
| **保真是否决条件** | 效果达标但改坏原意的候选会被采纳 |
| **受保护片段整句跳过** | 引用与直接引语被改写 = 学术不端 |
| **合并成一次改写** | 两次改写互相抵消，白花钱 |
| **降完不再跑格式规整**（前提：保真守住不可变项） | 每次改完都要全量重跑格式，成本高且用户会嫌烦 |

## 2.2 F1：三级定位怎么判

```python
# 精确：原文逐字出现在文档里
# 模糊：用序列相似度找最像的段落，超过阈值即认为"文档改过一版"
# 未定位：连最像的都低于阈值
```

**置信度**是相似度的归一化值，直接写进报告。用户看到 0.62 和 0.97
就能判断哪些需要重点核对。

## 2.3 F2：合并指令怎么构造

```python
def build_instruction(unit, targets) -> RewriteInstruction:
    wanted = set(targets)
    parts = []
    if "overlap" in wanted:
        parts.append(HINT_OVERLAP)   # 改结构，不是换同义词
    if "style" in wanted:
        parts.append(HINT_STYLE)     # 打散句长、删套话、补具体信息
    return RewriteInstruction(
        strategy=Strategy.REPHRASE,
        kind=classify(unit.text),    # 按内容类型选策略（数据密集 / 论述 / …）
        hint="\n".join(parts),
        rationale=_RATIONALE,
    )
```

**两段 hint 是拼在一起的，但语义上分属两个约束** ——
模型需要在一次生成里同时满足，这正是合并的意义。

## 2.4 F2：状态机

```python
for attempt in range(1, max_attempts + 1):
    candidates = rewriter.rewrite(request)      # 可能抛异常 → NO_CANDIDATE
    for cand in candidates:
        fid = check_fidelity(cand, unit.text)   # ① 否决条件
        if not fid.ok:                          → REJECTED_FIDELITY
        eff = measure_effect(cand, unit.text)   # ② 重合
        style = _style_improved(...)            # ③ 风格
        if overlap_ok and style_ok:             → ACCEPTED
        → REJECTED_EFFECT / REJECTED_STYLE
```

**六个状态**：`accepted` / `skipped_protected` / `no_candidate` /
`rejected_fidelity` / `rejected_effect` / `rejected_style`。

为什么要六个而不是"成功/失败"：报告要能回答**为什么没改成功**，
用户才知道下一步该人工重写、还是补信息、还是干脆接受。

# 第四部分：踩过的坑

## 坑 1：把"无候选"和"未达标"混为一谈

**现象**：以为没接模型时状态是"无候选"，测试断言 `no_candidate >= 1` 失败。

**根因**：缺省 `StubRewriter` 并不是返回空列表，而是**把原文原样返回**。
于是状态是"重合 100% 未达标"，不是"无候选"。

**教训**：**桩对象的行为本身也要写清楚。**
一个"什么都不做"的桩有两种写法（返回空 / 返回原文），
它们在报告里的含义完全不同。

## 坑 2：中文数字不在保真检查范围内

**现象**：想用「五个数据集 → 十个数据集」测"改数字被拦"，结果候选被采纳了。

**根因**：`check_fidelity` 的数字检查只认**阿拉伯数字**。中文数字没有词表。

**教训**：写测试时要先确认**被测的检查真的覆盖这个输入**。
否则测的是"我以为它管"，而不是"它真的管"。

这条同时是一条**已知局限**（见下）：中文数字改造不会被拦。

## 坑 3：合并阶段与旧的两个阶段并存

**现象**：一度同时存在 `copilot.quality.rewrite` / `copilot.quality.deai` /
`copilot.revise` 三套入口，不知道该调哪个。

**根因**：合并时保留了旧包（因为它们装着可复用的原语），
但没在文档里说清"原语 vs 策略"的分界。

**教训**：**合并两个模块时，必须同时明确"谁是策略、谁是原语"。**
否则读者会以为有三套并存的东西。

# 第五部分：已知局限

| 局限 | 说明 | 影响 |
|---|---|---|
| **中文数字不受保真保护** | 「五个」→「十个」不会被拦 | 事实性错误可能漏过 |
| **术语漂移抓不到** | 「召回率」→「查全率」保真通过 | 全文术语可能不一致（E6 取消后没人管） |
| **风格改善依赖诊断有内容** | 原文本来就没诊断出问题 → 风格校验形同虚设 | 报告说"形似 AI"但诊断为空时，降AI 目标无法验证 |
| **改写效果受限于改写器** | 缺省 `StubRewriter` 不产生有效候选 | 不接模型时这个阶段只能定位、不能改 |
| **未定位片段不自动处理** | 交回用户 | 报告基于旧版文档时，用户工作量大 |
| **不做跨片段一致性** | 每段独立改写 | 相邻段落可能风格突变 |
| **不验证"降重是否真的降了"** | 我们只用字面重合度度量，不重新提交外部查重 | 字面降了但语义相似度仍高的情形抓不到 |

### 关于最后一条的补充

我们用 `max_run`（连续重合字数）与 `containment`（n-gram 包含率）
作为**代理指标**，因为它们**确定、免费、可复现**。

但要诚实：**代理指标不等于外部查重结果。**
报告里已明确标注这一点。要拿到真实结论，只能改完再提交一次查重。
