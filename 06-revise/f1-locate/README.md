# E3 · 外部检测报告解析与定位

> **本文件是该模块的学习材料**：设计 + 讲解。按约定沉淀在此，便于复盘。
>
> 代码位置：`06-revise/f1-locate/src/copilot/quality/report_parse/`
> 测试：`06-revise/f1-locate/tests/`

## 层级定位

```
src/copilot/quality/report_parse/          ← 本包
        ├── 子部分 1  统一问题模型        models.py
        ├── 子部分 2  报告格式解析器      parsers.py
        ├── 子部分 3  片段定位           locate.py     ★ 核心
        └── 子部分 4  问题清单           checklist.py
```

## ★ 先说清楚：本模块**不做检测**

查重与 AI 检测由**外部工具**完成。用户拿着报告进来，本模块只做两件事：

1. **读懂报告** —— 把各家格式不一的报告统一成一种结构；
2. **定位回来** —— 报告里说"这段文字重复了"，到底是用户文档的第几行到第几行？

输出交给 E4 降重 / E5 降AI 去改写。

# 第一部分：设计

## 输入 / 输出契约

| | 内容 |
|---|---|
| **输入** | ① 外部工具的报告（JSON / CSV / 纯文本粘贴）② 用户的论文草稿 |
| **输出** | 统一问题清单：每条含 `原文片段 / 类型（重复·AI）/ 报告给的分数 / 来源文献（若有）/ 文档位置（行号区间）/ 定位置信度` |
| **不做** | 不做检测、不做改写（前者是外部工具的职责，后者是 E4/E5 的职责） |

## 本模块真正的难点

> **报告里的片段，来自「旧版本」的文档。**

用户在外部工具跑完检测，通常**还会继续改稿**。等他把报告拿进来时，
文档往往已经和报告生成时不一样了。所以：

```
报告片段："本文提出了一种基于图神经网络的推荐方法"
文档现状：  "本文提出了一种基于异构图神经网络的推荐方法"   ← 中间加了两个字
```

**精确匹配会失败。** 这时有三种做法，只有一种是好的：

| 做法 | 后果 |
|---|---|
| 静默丢弃 | 用户以为都处理了，其实漏了一处 —— **最危险** |
| 硬指一个位置 | 用户去改错误的地方，白费功夫还改错了 |
| **如实报"未定位" + 给出最接近的位置供参考** | ✅ 用户自己判断该不该改 |

这就是本模块的核心设计原则，与 E2 的「**宁可少绑定，不可绑错**」
是同一条：**不确定的时候，把不确定性如实交回给人，不要替人做决定。**

## 四个子部分：作用与「为什么需要」

### ① 统一问题模型 `models.py`

**作用**：定义一个与报告来源无关的问题条目结构 ——
原文片段、类型（重复 / AI）、报告给的分数、来源文献、文档位置、定位置信度。

**为什么需要**：知网、维普、PaperPass、GPTZero……每家报告的结构都不一样。
如果后面的定位与改写逻辑直接吃各家原始格式，会变成 N×M 的分支。
**统一模型是这几家的"防腐层"** —— 与 E1 的文档模型是同一个设计手法：
**把"会变的东西"（报告格式）挡在外面，让核心逻辑只面对一种结构。**

### ② 报告格式解析器 `parsers.py`

**作用**：把各家报告转成统一模型。设计成**注册表**：一种格式一个解析器。

**为什么需要**：格式会不断增加，而且**谁也无法预先支持所有格式**。
注册表让"新增一种报告格式"的成本 = 加一个函数，而不是改核心逻辑。

**刻意的设计取舍**：优先支持**「用户直接粘贴片段列表」**这种最朴素的形式。

**为什么**：PDF 报告的版式解析很脆弱（不同工具导出的 PDF 结构千差万别，
还有扫描件），而"把报告里那几段文字复制粘贴进来"是**零歧义**的。
先保证可靠的路径能用，再逐步加自动解析 —— 而不是反过来。

### ③ 片段定位 `locate.py` ★ 核心

**作用**：把报告里的片段，定位到用户文档的**具体行号区间**。

**为什么需要**：这是整个 E4/E5 链路的前提 —— **不知道改哪里，就无从改起。**

**怎么做的（三级策略）**：

| 级 | 策略 | 适用 |
|---|---|---|
| ① | **精确匹配**（规范化后逐字相同） | 文档没改过 |
| ② | **模糊匹配**（最长公共子串找最像的单元） | 文档改过一点，或报告有格式差异 |
| ③ | **如实报未定位** | 完全对不上 |

**为什么第 ③ 级是必须的、而不是失败处理**：
报告与文档对不上是**常态**（用户改过稿），不是异常。
把它当异常处理，结果就是静默丢弃或硬指位置 —— 两种都害用户。

**多对一的处理**：同一处文字可能被报告列了多条（重复 + 疑似 AI）。
按位置归并后交给下游，避免下游对同一段改两遍。

### ④ 问题清单 `checklist.py`

**作用**：汇总、去重、分级、排序，输出给 E4/E5。

**为什么需要**：
- **已定位 / 未定位分开列** —— 未定位的必须让用户看见（见上面的安全隐患）；
- **按位置排序** —— 用户是从上往下改的；
- **统计** —— "报告里 37 处，定位到 35 处，2 处未定位" 让用户知道处理了多少。

## 设计路线（实施步骤）

| 步 | 内容 | 产出 |
|---|---|---|
| 1 | 统一问题模型 | `models.py` |
| 2 | 文档切分（可定位单元） | `segments.py` ✅ 已就位 |
| 3 | 三级定位策略 | `locate.py` |
| 4 | 报告解析器（纯文本 / JSON / CSV） | `parsers.py` |
| 5 | 问题清单与报告 | `checklist.py` |
| 6 | 端到端样例（含"文档改过"的场景） | `examples/` |

## 验收标准

1. **报告片段与文档一致** → 精确定位到行，置信度标为"精确"；
2. **文档被改过**（片段部分对不上）→ 模糊定位，并**标明这是模糊匹配**；
3. **完全对不上** → **如实报"未定位"**，附最接近的位置供参考，**不硬指**；
4. **格式差异**（全角/半角、多余空格）**不影响**定位；
5. **同一处的多条报告条目** → 合并成一条，不重复输出。

## 关键设计判断

| 判断 | 理由 |
|---|---|
| **不为某家报告格式写死逻辑** | 报告格式会变、会增；统一模型是防腐层 |
| **优先支持"粘贴片段列表"** | PDF 版式解析脆弱，"复制粘贴"零歧义 —— 先保证可靠路径 |
| **定位失败必须显式报告** | 静默丢弃会漏改；硬指位置会让用户改错地方 |
| **置信度分三档并写进报告** | 用户需要知道"这条定位可不可信"才能决定要不要动手 |
| **按位置归并** | 下游对同一段文字只应改一次 |

# 第二部分：实现细节

## ① 统一问题模型 `models.py`

三个概念**刻意分开**，而不是合成一个类：

```python
FlaggedItem   # 报告说了什么（片段、类型、分数、来源）
LocatedItem   # 它在文档的哪里（位置 + 定位置信度）
Checklist     # 两者的集合
```

**为什么不合成一个类**：定位可能失败，而"报告说了什么"是确定存在的。
合成一个类就会出现「位置字段是 None 但对象依然存在」的半成品状态，
下游每处都要判空。

## ② 报告解析器 `parsers.py`

注册表 + 三种格式：

| 格式 | 形状判据 | 解析失败时 |
|---|---|---|
| `json` | 以 `[` / `{` 开头 | **直接报错**（`strict_shape=True`） |
| `csv` | 首行含逗号 | 退回纯文本（信号很弱） |
| `plain` | 任何非空文本 | — |

**★ `strict_shape` 的作用**：以 `[` 开头**就是** JSON 的形状，
解析失败说明内容有问题。这时如果降级成纯文本，
会把**整段 JSON 当成一条重复片段**，用户拿到的定位结果离奇且难查。
所以结构化格式解析失败时直接报错，而不是默默降级。

**字段别名兼容**：各家导出的字段名不统一，所以做了别名表
（`text`/`content`/`snippet`、`score`/`similarity`/`rate`）。

## ③ 片段定位 `locate.py` ★

### 三级策略

```python
# ① 精确：规范化 + 去空白后逐字查找
# ② 模糊：按可定位单元找最长公共子串最像的一段
# ③ 未定位：如实报告 + 给出最接近的位置供参考
```

### ★ 去空白匹配：为什么必须做，以及必须映射回原文

从 PDF 报告里复制文字，几乎必然带进多余空格、换行。
按原样比对，「方法，  并」和「方法，并」就对不上——而人眼里它们是同一句话。

做法是构造**去空白索引**，并**记录每个字符回到原文的偏移**：

```python
def _strip_with_map(text):
    chars, pos_map = [], []
    for i, ch in enumerate(text):
        if not ch.isspace():
            chars.append(ch)
            pos_map.append(i)
    return "".join(chars), pos_map
```

查找后映射回去：

```python
hit = index.stripped.find(needle_stripped)
start = index.pos_map[hit]                                    # ← 回到原文
end   = index.pos_map[hit + len(needle_stripped) - 1] + 1
```

**这一步是关键**：去空白是为了比对，但**偏移必须回到原文**。
如果直接在去空白文本上算偏移，定位就会错，而且不报错。

### `DocIndex` 为什么单独成对象

一次解析可能有几十条报告条目。如果每条都重新规范化全文、重建映射，
复杂度是 O(条目数 × 全文长度)。**索引只建一次**，之后每条都是 O(查找)。

### 模糊匹配的阈值

```python
DEFAULT_FUZZY_MIN_RATIO = 0.6   # 命中长度 / 报告片段长度
DEFAULT_FUZZY_MIN_RUN   = 10    # 绝对最短命中长度
```

**两个都要**：只看比例，一个 5 字的片段命中 4 字就是 80%，但那可能是巧合；
只看绝对长度，一个 500 字的片段命中 60 字（12%）也会被当成定位成功。

### 未定位时的 note

```python
note = f"最接近的是第 {unit.line + 1} 行，但只命中 {run} 字（{ratio:.0%}），
        低于 {fuzzy_min_ratio:.0%} 的阈值，故不作为定位结果"
```

**给出参考位置但不作为结果** —— 用户能知道该往哪看，但不会被误导去改错地方。

## ④ 问题清单 `checklist.py`

`by_location()` 按位置归并：

**为什么下游需要归并**：同一段文字可能同时被判「重复 + 疑似AI」，
或被查重报告按不同来源列了多条。不归并的话，
E4 会对同一段改好几遍。

# 第四部分：踩过的坑

## 坑 1：`build_checklist("")` 去读了当前目录

`Path("")` 被解析成 `.`，而 `exists()` 对它返回 **True** ——
于是代码去"读目录"，抛 `PermissionError`。

**修复**：用 `is_file()` 而不是 `exists()`，天然排除目录。

**教训**：`Path("").exists()` 为真这件事反直觉，但它是标准行为。

## 坑 2：JSON 解析失败被静默降级成纯文本

用户粘贴的 JSON 少了个括号 → `can_parse` 通过、`parse` 失败 →
降级到纯文本 → **整段 JSON 被当成一条重复片段**。

**修复**：给解析器加 `strict_shape`，形状明确的格式失败时直接报错。

**教训**：「尽量不报错」在某些场景下是有害的 ——
它会把手误变成一个更难查的错。

## 坑 3：多余空格导致定位失败

报告片段带两个空格、文档里没有空格 → 精确匹配失败，
模糊匹配命中率只有 42% → 判为未定位。

**修复**：去空白索引（见上）。这是本模块最重要的一个实现细节。

# 第五部分：已知局限

| 局限 | 说明 |
|---|---|
| **不支持 PDF / HTML 直接解析** | 版式解析脆弱（不同工具导出的结构千差万别，还有扫描件）。当前优先保证「粘贴片段列表」这条零歧义路径 |
| **未定位条目不猜测位置** | 这是刻意设计，不是缺陷。但用户需要自己去找 |
| **模糊匹配阈值是经验值** | 0.6 / 10 两个值没有标注数据支撑，属先验设定 |
| **不处理跨段落的长片段** | 若报告片段跨越多个段落且中间有删改，可能定位失败 |
| **同一片段多处出现时只报第一处** | `str.find` 返回首个命中 |
| **不做检测** | 查重/AI 检测由外部工具完成，本模块只负责读懂与定位 |
