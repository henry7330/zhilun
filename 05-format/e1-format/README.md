## 六个子部分：作用与「为什么需要」

### ① 文档模型 `docmodel.py`

**作用**：把 Markdown 草稿解析成**结构化视图** —— 章节树、参考文献条目列表、
图表题注、正文里的交叉引用。每个元素都记**行号**。

**为什么需要**：所有规则都需要"文档的结构化视图"。不做这一层会怎样 ——
每条规则各自用正则去扫原始文本：章节识别逻辑会**被重复实现 N 遍**；
改一处正则，N 条规则一起崩；更糟的是**跨规则的检查做不了**
（"图 3 被引用了但整篇没有图 3"需要同时知道题注与引用）。

**关键设计**：这一层是**防腐层**。规则只看文档模型，**永远不看原始 Markdown**。
将来支持 DOCX / LaTeX 时，只需再写一个解析器产出同样的模型，**六条规则一行不改**。

### ② 模板配置 `template.py`

**作用**：用**声明式数据**描述"什么算合格"：必需章节、章节顺序、
参考文献风格、正文字数下限。

**为什么需要**：格式要求**因学校/期刊而异**。若把要求硬编码进规则代码，
换一个学校就要改代码，而且规则代码会退化成一堆 `if 学校 == ...`。
声明式配置把「**要求是什么**」与「**怎么检查**」分离。

### ③ 结构校验规则 `rules/structure.py`

**作用**：检查必需章节是否齐全、顺序是否正确、层级是否规范、字数是否达标。

**为什么需要**：这是**论文被打回的最常见原因**，而且**完全可判定** ——
"有没有'结论'这一章"是客观事实，不需要任何智能。

### ④ 参考文献格式规则 `rules/reference.py`

**作用**：把每条参考文献解析成结构化字段，再按 GB/T 7714 等风格逐条校验。

**为什么需要**：参考文献是**格式要求最琐碎、人工核对最痛苦**的部分 ——
30 条文献，每条要看类型标识、作者数、标点、年份。而它**天然是结构化的**
（`作者. 题名[J]. 刊名, 年, 卷(期): 页码.`），非常适合规则化。

### ⑤ 图表与交叉引用规则 `rules/figures.py`

**作用**：检查图表编号是否连续、正文引用的图表是否存在、题注是否规范。

**为什么需要**：长文里"见图 3"但图已被删、或编号跳号（图1、图2、图4），
**人工需要通读全文才能发现**。这类「全局一致性」问题正是机器擅长的。

### ⑥ 问题报告 `report.py`

**作用**：汇总各规则产出，按严重级分类、按位置排序，输出人可读报告与结构化数据。

**为什么需要**：**校验的价值取决于"问题好不好修"**。
一堆没有分级的告警等于没有告警。

## 设计路线（实施步骤）

| 步 | 内容 | 产出 |
|---|---|---|
| 1 | 文档模型 + 测试 | `docmodel.py` |
| 2 | 模板配置 | `template.py` |
| 3 | 三类规则（规则码 + 严重级 + 检测 + 修法） | `rules/*.py` |
| 4 | 报告汇总 | `report.py` |
| 5 | 端到端样例：故意埋了各类问题的草稿 | `eval/dataset/sample_thesis_draft.md` |
| 6 | 跑出报告 | `reports/format_report.md` |

## 验收标准

1. 埋了 N 处问题的草稿 → **逐条全部检出**；
2. 合格草稿 → **误报为 0**（没有这条，规则写得越严越好就是在自欺）；
3. 每个问题都能给出**行号**与**修法提示**；
4. 全程**零新依赖**，可离线运行。

## 关键设计判断

| 判断 | 理由 |
|---|---|
| **文档模型是防腐层** | 规则与输入格式解耦，加 DOCX 支持时规则不动 |
| **规则码稳定**（如 `REF001`） | 便于统计、忽略、回归测试；让报告可被程序消费 |
| **配置与引擎分离** | 一所学校一份配置，而不是一份代码 |
| **只报告、不修改** | 格式修改涉及用户意图，自动改容易制造新问题 |
| **不判学术不端** | 那是 E7 合规的职责，本模块只谈格式 |

# 第二部分：实现细节

## ① 文档模型

**三遍解析，顺序有讲究**：

```python
# 第一遍：先确定「参考文献」章节的行区间
ref_start, ref_end = ...
def in_ref_block(line_no): ...

# 第二遍：构建章节树（用栈处理层级）
while stack and stack[-1].level >= level:
    stack.pop()

# 第三遍：题注 / 交叉引用 / 参考文献条目
```

**为什么必须先划出参考文献区间**：否则文献题名里的"图"会被当成正文引用
（《基于图神经网络的…》这类题名太常见），一旦误扫就刷出一堆"引用了不存在的图"。

**章节归一化**是模板匹配的成败关键：

```python
_NUM_PREFIX = re.compile(
    r"^(?:"
    r"第\s*[一二三四五六七八九十百千\d]+\s*[章节篇]|"   # 第一章
    r"\d+(?:\.\d+)*|"                                   # 1.2
    r"[一二三四五六七八九十]+|"                          # 一、
    r"[（(]\s*\d+\s*[)）]"                               # （2）
    r")[.、,，:：\s]*"
)
```

「2.1 文献综述」与「文献综述」必须视为同一章节，否则模板写「文献综述」
就永远匹配不上带编号的标题。

## ② 模板配置

```python
@dataclass
class Template:
    name: str
    required_sections: list[str]        # 顺序即要求顺序
    section_order_strict: bool = True
    reference_style: str = "gbt7714"
    min_body_words: int | None = None   # None = 不检查
    max_authors_before_etal: int = 3
```

**未知字段直接报错，而不是静默忽略**：

```python
unknown = set(data) - known
if unknown:
    raise ValueError(f"模板里有未知字段：{', '.join(sorted(unknown))}")
```

用户把 `min_body_words` 写成 `min_words` 却以为生效了 —— 这是最难查的一类问题。

## ③ 结构校验

顺序检查有一个**刻意的抑制**：

```python
if template.section_order_strict and not missing:
```

**章节有缺失时不判顺序** —— 否则「方法」缺失会导致后面全部错位，
同一根因刷出一串误报。

`SEC005`（空章节）**只看叶子章节**：有子章节的章节不参与本检查，
因为"某一章直接进入 2.1 / 2.2，自己没有引言段"是完全常见的合法写法。

## ④ 参考文献规则

**设计取向：宁可漏报，不可误报。**

```python
def _parse_reference(raw, index, line) -> Reference:
    """这里只做**保守抽取**：宁可抽不到（字段为 None），也不要抽错。
    抽错会让格式规则报出**假的错误**，比漏报更伤信任。
    """
```

作者数超限这条规则加了保险：

```python
n = len(ref.authors)
if n > template.max_authors_before_etal and not _has_etal(ref):
```

**只在作者确实抽出来了、且超过阈值时才报**，避免"抽取失败"被误判成"作者数不合法"。

## ⑤ 图表与交叉引用

支持两种编号体系：

```python
def _group_key(number: str) -> tuple[int, ...]:
    """「图 2-1 / 2-2 / 2-3」应在"第 2 章"这一组里连续，
    而不是要求全文从 1 连续到 N。"""
    return tuple(_parts(number)[:-1])
```

**三级严重度的分配是有判断的**：
- `FIG002`（引用了不存在的图）→ **ERROR**：读者按图索骥会找不到东西
- `FIG003`（图没被引用）→ **INFO**：可能是疏漏，也可能是排版需要，由作者决定

**题注 vs 正文的歧义处理**（词法上无法完全区分，如实标注为启发式）：

```python
def _looks_like_caption(remainder: str) -> bool:
    text = remainder.strip()
    if _PROSE_TAIL.search(text):      # 以「。！？；」结尾 → 是正文句子
        return False
    if len(text) > _CAPTION_TEXT_MAX: # 太长 → 是句子不是题注（给英文兜底）
        return False
    return True
```

## ⑥ 问题报告

```python
@dataclass(frozen=True)
class Issue:
    code: str        # 稳定编号，如 REF001
    severity: Severity
    message: str
    line: int | None
    fix: str
```

排序按**严重级 → 行号**：
```python
self.issues.sort(key=lambda i: (i.severity.rank, i.line if i.line is not None else 10**9))
```
因为用户是**从上往下改的**。

# 第三部分：★ 端到端样例抓出的 3 个 bug

**这一节比上面六个子部分加起来更值得记住。**

| # | Bug | 后果 | 为什么单测没抓到 |
|---|---|---|---|
| 1 | 交叉引用正则用 `(?<![\w])` 前瞻，而 **`\w` 匹配汉字** | 「如图 3 所示」**全部漏扫** → 双向出错：该报的漏报，不该报的误报 | 单测写的是「如 图 9 所示」，**中间有空格**，恰好绕过 bug |
| 2 | 章节编号正则漏了 **「第X章」** | 用「第一章 绪论」的草稿，5 个必需章节**全部误报缺失** | 单测只覆盖了 `1.2` / `一、` / `（2）` |
| 3 | 「图 3 给出了结果。」这类**以图表编号开头的正文句子**被误判为题注 | 它不再算引用 → 反向误报「图 3 未被引用」 | 单测的题注与正文在行首形式上区分明显 |

**三个 bug 里有两个是"恰好绕过"型的** —— 测试用例**无意中避开了缺陷**。

> **核心一课：单元测试全绿 ≠ 功能正确。**
> 写单测时人会不自觉地在自己设想的那种格式上验证，
> 而真实文档的写法千变万化。**必须有一份"真实一点"的端到端样例**，
> 而且要故意写得跟单测不一样。

三个 bug 现在都有回归测试（测试名里带「回归」）。

# 第五部分：已知局限（如实记录）

| 局限 | 说明 |
|---|---|
| **输入只支持 Markdown** | DOCX / LaTeX 需另写解析器（但规则不用改，见防腐层设计） |
| **题注/正文的区分是启发式** | 「图 N」开头的行靠标点与长度判断，词法上无法完全确定；英文长句可能误判 |
| **GB/T 7714 只覆盖核心检查** | 类型标识 / 年份 / 序号 / 作者数；完整标点规范尚未实现 |
| **参考文献字段抽取偏保守** | 宁可抽不到也不抽错，因此部分真问题会漏报 |
| **未校验字体字号页边距** | 那些信息不在 Markdown 里，属于 DOCX 层 |
| **不做内容质量判断** | 那是 E6 审稿挑错的职责 |
