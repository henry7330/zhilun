# 第一部分：设计

## 1.1 这个 Agent 解决什么问题

论文写完了，但学校的格式要求还没满足：标题该黑体三号居中、正文该宋体小四、
参考文献该按 GB/T 7714 著录……

**逐条对着要求改一遍，是纯体力活，而且极容易漏。**

这个阶段把"检查"升级成"规整"：

```
用户给格式要求 ──▶ 系统按要求改文件 ──▶ 告诉你改了哪里、还有什么没管
```

## 1.2 ★ 为什么是"规整"而不是"校验"

旧设计（E1 格式校验）只**报问题**：

```
❌ 第 3 行：标题没有居中
❌ 第 18 行：参考文献格式不符合 GB/T 7714
```

用户拿到这份清单，还得自己一条条去改。**报问题不等于解决问题。**

新设计直接**改文件**，并给出一份"改了什么"的 diff。

| | 校验 | 规整 |
|---|---|---|
| 产出 | 问题清单 | 改好的文件 + diff |
| 用户下一步 | 自己去改 | 核对 diff 后直接用 |
| 价值 | 发现问题 | 解决问题 |

## 1.3 边界：我们不做什么

| 不做 | 谁做 | 为什么 |
|---|---|---|
| **核查引用是否真实** | B 阶段（B3 核实）+ D 阶段（D4 约束来源） | 两道关已经覆盖，不需要第三道 |
| 推测"你没写但可能需要"的格式项 | **人** | 擅自加要求会改坏论文 |
| 改正文内容 | — | **只改格式，不改内容**（写死在节点说明里） |

### 关于"不做引用真实性核查"的完整理由

引用真实性在这条链路里有两道关：

```
B3 引用管理  ──▶ 核实 DOI / 在文献库里查证 → 只有核实过的才进库
D4 文献引用  ──▶ 正文引用的每一篇必须来自那个库
```

**入口核实 + 使用约束**，比"事后再查一遍"更严，也更省。
所以格式规整阶段不需要重复这件事。

## 1.5 每个子部分：作用 + 为什么需要

### ① E1 格式规整

**作用**：按用户给的格式要求，用 LLM 直接改文件；同时给出 diff 与未覆盖项清单。

**为什么需要**：这是"规整"与"校验"的分界线。没有它，本阶段就退回到报问题。

**不做会怎样**：用户拿到的还是清单，还是得自己改 —— 本阶段就没有存在价值。

### ② E2 文本一致性

**作用**：术语是否全篇统一、摘要里的关键词正文有没有出现、章节篇幅是否失衡、图表引用是否断裂。

**为什么需要**：这些是**改写与规整之后最容易坏掉的东西**。
格式一改（比如某章拆成两节），图表编号可能就断了。

**不做会怎样**：格式看起来规整了，但正文里"见图 3"指向一个不存在的图。

**★ 为什么它不叫"格式"检查**：术语一致是**内容**一致，不是版式。
放在报告里必须单独成段（`## 文本一致性（非格式）`），
否则用户读到"格式规整通过"会以为内容也没问题。

### ③ E3 导出

**作用**：产出 BibTeX、GB/T 7714 参考文献表、LaTeX 骨架，并**回读校验**。

**为什么需要**：规整完的稿子总得变成可交付的文件。
而"回读校验"是这一段最有价值的部分（见下）。

**不做会怎样**：用户拿到 Markdown，参考文献格式还得自己排。

### ④ 回读校验：为什么它是这套设计里最值钱的东西

生成代码经常"自检通过、产物是错的"，因为自检校验的是**逻辑**
（"我按逻辑写了 N 个 `\section`"），而不是**产物**（"文件里真的有 N 个"）。

回读校验换了个方向：**读回生成的文件，跟原稿逐项比对**。

| 比对项 | 抓什么 |
|---|---|
| 章节数 | 有章节被吞掉 |
| 每个章节标题 | 标题丢失或被改写 |
| 图表数 | 图表在导出时丢失 |
| 参考文献条数 | 文献少了几条（**肉眼极难发现**） |

**实测它就抓到了一个真 bug**（见第四部分坑 1）。

## 1.6 关于「一段式」：为什么这样选，以及它的代价

你选的是：**LLM 直接读格式要求并输出改好的文件**，不先产出结构化规范。

| | 一段式（当前） | 两段式（另一种设计） |
|---|---|---|
| 步骤 | 读要求 → 直接改 | 读要求 → 出结构化规范 → 人确认 → 确定性应用 |
| 速度 | 一次调用 | 多一次确认 |
| 可复核性 | **只能事后看 diff** | 规范本身可复核、可版本化 |
| 出错风险 | LLM 可能漏改/改错/顺手改内容 | 规范可审，应用过程确定 |

**选了一段式，代价就得兜住。** 所以 E1 内置两件事：

1. **改前快照 + diff** —— 告诉你哪些行变了、变成什么；
2. **回读校验** —— 改完用确定性规则再扫一遍，看问题数是否真的减少。

> **它不是"完全不管"，而是"事后能查"。**

## 1.7 关于「用户没提到就不改」

这条规则是对的（擅自加要求会改坏论文），但有个副作用：

**如果学校要求里没提图表编号，而原文编号是乱的，规整后仍然乱 ——
但用户会以为"格式规整过了 = 格式没问题"。**

所以 E1 会输出**未覆盖项清单**：

```
以下常见格式项你的要求里没提到，本次未处理：
标题层级与编号、正文字体/字号/行距、页眉页脚与页码、公式编号…
```

**这是"诚实"的具体实现**：不只说做了什么，还要说没做什么。

## 1.8 设计路线

| 步 | 内容 | 产出 | 验收标准（可判定） |
|---|---|---|---|
| 1 | 内容卫生检查 | `check_submission` | 占位符（TODO/XXX）、敏感信息（手机号/身份证）、匿名性违规都能检出 |
| 2 | 一段式规整 | `formatter(draft, requirement)` | 有 formatter 且给了要求 → 文件被改；否则如实说"未做版式规整" |
| 3 | diff | `_diff_summary` | 有改动必须给 diff；行数变化也要报 |
| 4 | 回读校验 | 重跑卫生检查 | 改完问题数应减少；没减少要警告 |
| 5 | 未覆盖项 | `COMMON_FORMAT_ITEMS` 比对 | 要求里没提到的常见项要列出来 |
| 6 | 一致性检查 | `review_document` | 术语/关键词/篇幅/图表四类都能出 |
| 7 | 导出 + 回读 | `export_paper` | 产物与原稿的章节数、标题、图表数、文献数逐项一致 |

## 2.2 E1 的实现要点

```python
# ① 无论是否接入 LLM，内容卫生检查都要跑
hygiene = check_submission(draft, anonymity_required=...)

# ② 有 formatter 且给了要求 → 一段式改文件
if formatter and requirement.strip():
    result_text = formatter(draft, requirement)     # 失败要捕获并如实报
    diff = _diff_summary(draft, result_text)        # 行级 diff
    after = check_submission(result_text, ...)      # 回读：问题数减少了吗
else:
    # ★ 不能说"规整好了" —— 要如实说没做
    finding("未做版式规整（未提供格式要求 / 未接入 LLM）")

# ③ 未覆盖项清单
uncovered = [i for i in COMMON_FORMAT_ITEMS if i not in covered]
```

**注意 `formatter` 抛异常的处理**：捕获后报 ERROR，且**不改动文件**。
不能因为"改了 90% 就存 90%"——半成品比原稿更难排查。

# 第四部分：踩过的坑

## 坑 1：★ 扁平标题导致整篇被丢光

**现象**：导出 LaTeX 时，`\title{摘要}` 之后**什么都没有** ——
3 个章节一个都没渲染出来。而导出函数自己返回 `ok=True`。

**根因**：导出器有一条启发式：

```python
if roots[0].title == resolved_title:
    roots = roots[0].children      # ← 假定第一个标题是"书名"，从它的子章节开始渲染
    level_offset = -1
```

它假定文档是**容器式**（`# 论文题目` + `## 各章`）。但中文论文极常见的写法是**扁平标题**：

```
# 摘要        ← 这是第一章，不是书名
# 方法
# 结论
```

此时 `roots[0].children` 是**空列表** → 什么都不渲染。

**怎么被发现**：**回读校验**。原稿 3 章 vs 产物 0 章 → 报错。
如果是"生成时自检"，它会说"我按逻辑写了 3 个 section"，然后通过。

**修法**：只有第一个标题**确有子章节**时，才把它当文档名。
`resolve_title` / `latex.py` / `verify.py` 三处一起改（它们共享同一个假设）。

**教训**：
> **一个"看起来显而易见"的启发式，往往只对作者当时想到的那一种写法成立。**
> 而"回读校验"是唯一能抓住这类错误的东西 —— 因为它比对的是**产物**，不是**逻辑**。

## 坑 2：把"节点执行成功"当成"检查通过"

**现象**：`test_stage_flags_foreign_reference` 断言 `not d4.ok` 失败 ——
明明有 ERROR 级发现，`d4.ok` 却是 True。

**根因**：`NodeResult.ok` 的语义是"**这个节点有没有跑崩**"，不是"检查有没有通过"。
检查结论看 `StageReport.can_submit`（由 Finding 的 severity 汇总）。

**教训**：**一个字段只有一个含义。** 把"执行成功"和"检查通过"混在一处，
会让报告在两种失败下给出同一个信号，用户就分不清"系统坏了"还是"稿子有问题"。

## 坑 3：搬目录把语料路径弄丢了

**现象**：`run_retrieval_eval.py` 报 `FileNotFoundError: 语料缓存不存在：None`。

**根因**：`find_corpus()` 是从模块所在位置**向上**找 `eval/dataset/corpus.json`。
`00-core` 移到系统根之后，向上走只能到 `zhilun/`，
而 `eval/` 在 `05-format/` 下面 —— 永远找不到。

**修法**：除了向上找，再**向下看一眼**一层子目录（`*/eval/dataset/corpus.json`）。

**教训**：
> **"向上查找"比"数层级"健壮，但仍假设了固定的相对位置。**
> 目录结构一变，凡是靠位置找东西的代码都会静默失效。
> 加一条"向下也找一层"，成本很低，覆盖了阶段内挂载的情形。

# 第五部分：已知局限

| 局限 | 说明 | 影响 |
|---|---|---|
| **一段式不可复核** | 只有 diff 能看，没有结构化规范 | LLM 顺手改了正文内容，diff 里能看出但不一定有人逐行看 |
| **未覆盖项只是提示** | 不会补做，也不会阻止 | 用户可能忽略"页眉页脚没检查" |
| **格式要求靠 LLM 理解** | 要求写得含糊，改出来就含糊 | 建议把要求写具体（"标题：黑体三号居中"而不是"标题要规范"） |
| **E2 的术语检查需要全篇** | 章节标题不规范时可能漏检 | 见 `COMMON_SECTION_NAMES` 的说明 |
| **导出只到 LaTeX/BibTeX** | 不做 Word / PDF | 需要额外依赖（python-docx / LibreOffice），当前未实现 |
| **不改内容** | 只改格式 | 内容问题归 D 阶段与 E2 |
| **不核对引用真实性** | 刻意不做 | 由 B3 + D4 覆盖 |

### 关于"一段式"最实在的一条

如果哪天发现"LLM 规整后正文被改坏"成了常见问题，
**那就该换成两段式**（先出结构化规范，人确认后再确定性应用）。

代码结构已经为此留好了位置：`formatter` 是一个可替换的 callable，
换成"两段式"只需要换掉它，E2/E3 一行都不用动。
